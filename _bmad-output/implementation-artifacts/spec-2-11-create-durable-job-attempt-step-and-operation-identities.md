## Intent

**Problem:** Nothing records background work. Stories 2.6 to 2.8 reserve, run and reconcile paid work, and need a unique identity for every Job, attempt, step and external operation so a duplicate command cannot duplicate work or a charge, and a retry cannot start while an earlier charge is unresolved.

**Approach:** A Jobs-owned closed schema `jobs` with the four record families, an immutable command-receipt table, six narrow `api` commands, forward-only guarded states and one derived public state. A typed server-side module wraps the commands. There is no screen, dispatch, reservation or worker yet.

## Boundaries & Constraints

**Always:** Consult `node_modules/next/dist/docs/` before any Next.js code (AGENTS.md); none is expected. No new npm dependency, environment variable, secret, route, Server Action, page or copy in `lib/i18n`. New migration `20261023120000_job_records.sql`, additive. **Schema** `jobs`, closed like `usage` (revoke from browser roles, default privileges, no `anon`/`authenticated` access; `api` stays functions only). **Tables** (all ids `uuid`, every row carries `account_id`, times are `clock_timestamp()` UTC, ownership by composite foreign keys, `restrict`): `jobs.jobs` (`id`, `project_id` with `(project_id, account_id)` to `projects.projects(id, account_id)`, `kind` matching `^[a-z][a-z0-9_]{0,39}$`, `created_at`); `jobs.attempts` (`id`, `job_id`, `number` from 1, `previous_attempt_id` null only for 1, `input_digest` 64 lowercase hex, `state`, `stage` (same pattern as `kind`), `reason`, `created_at`, `started_at`, `ended_at`; unique `(job_id, number)`; unique `(job_id)` where `state in ('waiting','running')`, so a Job has at most one open attempt); `jobs.steps` (`id`, `attempt_id`, `step_key` same pattern, `created_at`; unique `(attempt_id, step_key)`); `jobs.operations` (`id`, `step_id`, `ordinal` 1 to 100, `state`, `request_id` null or 1 to 200 printable ASCII without spaces, `created_at`, `dispatched_at`, `outcome_at`; unique `(step_id, ordinal)`); `jobs.commands` (`account_id`, `command_id`, `kind`, `digest`, `subject_id`, `created_at`; primary key `(account_id, command_id)`). `jobs.jobs`, `steps` and `commands` refuse update and truncate; `attempts` and `operations` refuse truncate and every update except the guarded transitions below, never change an identity column, never leave a terminal state, and write `started_at`, `ended_at`, `dispatched_at`, `outcome_at` and `request_id` once; delete stays allowed (Epic 8 purge). **Attempt states** `waiting`, `running`, `completed`, `failed`, `cancelled`; moves `waiting→running`, `waiting→cancelled`, `running→completed|failed|cancelled`; stored reason is null for `waiting`, `running`, `completed`, `step_failed|lease_lost` for `failed`, `user_cancelled|account_disabled` for `cancelled`. **Operation states** `planned`, `dispatched`, `completed`, `ambiguous`, `noncharge`, `settled`, `abandoned`; moves `planned→dispatched|abandoned`, `dispatched→completed|ambiguous|noncharge`, `ambiguous→settled|noncharge`; `noncharge` needs a `request_id`; a stored `request_id` never changes. An operation is **potentially chargeable** while `dispatched` or `ambiguous`; **reconciled** or terminal are `completed`, `noncharge`, `settled`, `abandoned`. **The gate:** internal `jobs.charge_open(job, before_number)` is true when any operation of any attempt of the Job numbered below `before_number` is potentially chargeable. **Public state** of a Job is its highest attempt's `(state, stage, reason)` from internal `jobs.public_state`, which is the stored values except a `waiting` attempt's reason, which is derived: `awaiting_reconciliation` when `charge_open` for its number, else `awaiting_dispatch`. A Job has no state column. **Stage** is `accepted` at attempt 1, `retry` at later attempts, `started` when it starts, the step key when `begin_step` creates a step, and is left as it was when the attempt ends. **Commands** (the five writes and the read are `security definer`, `set search_path = ''`, `grant execute` to `service_role` only, composite outcome types named so they do not clash with `api.job_claim`, `api.job_finish`, `api.job_last`, `lifecycle.job_receipts`): the five writes take `p_account_id`, `p_epoch` and `p_command_id` (the read takes no command ID and only the checks it needs) and run in this order: arguments (22023); `identity.assert_operation_authority` in `begin/exception when sqlstate 'N3010'` (`denied`); advisory lock `nova3d:jobs-command:<account>:<command>`; the subject belongs to the Account and its Project row is locked `FOR SHARE`, not deleted, not tombstoned (`unavailable`, one answer for foreign, deleted, unknown and tombstoned); advisory lock `nova3d:job:<job>`; the receipt by `(account, command_id)`, where the same digest replays (`replayed`, the original receipt) and another is `reused`; then the command's own checks. The digest is `sha256` over the kind and every caller-supplied argument except Account, epoch and command ID (as `projects.length_prefixed`). Every command that answers `replayed` or does its work leaves a `jobs.commands` row, so a second command ID that finds the work already done is recorded and replays too. `api.accept_job(…, p_project_id, p_kind, p_input_digest)` creates the Job and attempt 1 (`waiting`, stage `accepted`): `created|replayed|reused|denied|unavailable`. `api.begin_step(…, p_attempt_id, p_step_key, p_ordinal default null)`: records that already exist are returned and never recreated, whatever the attempt's state; otherwise the attempt must be `running` (`not_running`, carrying its state) and the step, and with an ordinal its `planned` operation, are created and the stage set: `created|replayed|reused|denied|unavailable|not_running`. `api.advance_operation(…, p_operation_id, p_to, p_request_id default null)` follows the moves above; `planned→dispatched` needs its attempt `running` (`not_running`); every other move works in any attempt state, so a late outcome of an ended attempt is still recorded; asking for the state it is already in with the same `request_id` replays; a move not listed, a missing `request_id` for `noncharge`, or a changed `request_id` is `invalid_transition` carrying the state: `advanced|replayed|reused|denied|unavailable|not_running|invalid_transition`. `api.move_attempt(…, p_attempt_id, p_to, p_reason default null)`: `running` is refused `blocked` (carrying `awaiting_reconciliation`) while `charge_open` and sets `started_at` and stage `started`; `completed` is refused `open_operations` while any of its operations is `planned`, `dispatched` or `ambiguous`; `failed` and `cancelled` need a reason from the closed set, set `ended_at` and in the same transaction turn its `planned` operations `abandoned` (its `dispatched` and `ambiguous` operations stay potentially chargeable); a move not listed is `invalid_transition`: `moved|replayed|reused|denied|unavailable|blocked|open_operations|invalid_transition`. `api.request_retry(…, p_job_id, p_expected_number, p_input_digest)`: `stale` (carrying the highest number) when the highest attempt's number differs; `not_retryable` (carrying its state) unless that attempt is `failed`; otherwise creates attempt `number+1` linked to it, `waiting`, stage `retry`, and returns its derived reason; it never waits inside the transaction and never starts the attempt: `created|replayed|reused|denied|unavailable|stale|not_retryable`. `api.read_job(p_account_id, p_epoch, p_job_id)`: `found|denied|unavailable`; the Job, its public state, `can_retry` (the highest attempt is `failed`), and every attempt in order with its state, stage, reason, times and count of potentially chargeable operations; nothing else. Only `accept_job` and `request_retry` insert attempts; no code path retries by itself. **Replays and gates run before state checks**, so a lost answer always replays. `api.preflight` is re-created from `usage_limits.sql:660-923` keeping every earlier statement, with a Story 2.11 block (the `jobs` tables and the six signatures, 47 in all) raising `N3020`; end with `notify pgrst, 'reload schema'`. **`lib/job-records.ts`**: the only caller of the six functions (add it to the four `callApi`/`callRow` allow-lists on purpose), typed with outcome unions validated by `oneOf` and `unexpected()` as `lib/usage.ts`, exporting the state, reason, stage and operation-state vocabularies and a pure `isChargeable(state)`; it has no caller yet (pinned as `lib/project-target.ts` is) and no word `tombstone` in code.

**Ask First:** Allowing a retry from a `cancelled` or `completed` attempt; any automatic retry or any wait inside a command; storing a state on the Job; extra reason codes or a closed `kind` list; fields for reservations, rates, provider, model, leases, fencing, signing, the outbox or results (Stories 2.6 to 2.8); a screen, route, notification or `lib/i18n` copy; an audit event; writing `jobs` rows from application code other than through the six commands; any step against staging, production, Railway, GHCR or Backblaze.

**Never:** Dispatch, outbox, workers, leases, signing or fencing tokens (2.7); reservations, settlements, rates or ledger entries (2.4, 2.6); the reconciliation process (2.8); the Job detail screen (2.7); editing a finished row; reusing an operation ordinal or a step key within an attempt; reclaiming a terminal attempt; any number or request in a Job a foreign Account can read; changing the Account disable or its cancellation; editing an expectation to make a test pass except the pins this spec names.

## I/O & Edge-Case Matrix

| Scenario | Input / State | Expected Output / Behavior | Error Handling |
|----------|--------------|---------------------------|----------------|
| Accept | A new command on an own, live Project | One Job and attempt 1: `waiting`, stage `accepted`, reason `awaiting_dispatch`; `created` | N/A |
| Replay / reuse | Same command ID again / with another kind, Project or digest | `replayed`, the same Job and one row / `reused`, nothing written | N/A |
| Duplicate step | Two commands (two IDs) for the same attempt, step key and ordinal 1 | One step, one operation; the second answers `replayed` with the original IDs and is recorded; the first ID with ordinal 2 is `reused` | N/A |
| Uniqueness | Another key, another ordinal on an existing step, or no ordinal | New step / new operation on the same step / a step with no operation; a repeated pair never adds a row | N/A |
| Not running | `begin_step` or `planned→dispatched` on a `waiting`, `failed`, `cancelled` or `completed` attempt | `not_running` with the state; nothing created; existing records still replay | N/A |
| Operation moves | `planned→dispatched→completed`, `→ambiguous→settled`, `→noncharge`; backwards, skipped, from terminal | The listed moves succeed and stamp times; others `invalid_transition` with the state; `noncharge` without `request_id` is refused | N/A |
| Retry gated | Failed attempt 1 with a `dispatched` or `ambiguous` operation; retry | Attempt 2 `waiting`, reason `awaiting_reconciliation`; starting it is `blocked`; a third attempt or any number change cannot pass; after `settled`, `noncharge` or `completed` the reason reads `awaiting_dispatch` and start succeeds | Wait, reconcile, start |

| Terminal | A `failed`, `cancelled` or `completed` attempt: start, begin a step, dispatch, direct update | Refused; the row never changes | N/A |
| End an attempt | Fail or cancel with `planned`, `dispatched`, `ambiguous` operations; complete with open ones | `planned` become `abandoned`; the others stay chargeable; completion is `open_operations` | N/A |
| Public state | Any Job | `read_job` state, stage and reason equal the stored attempt (derived reason for `waiting`); the Job's state is its highest attempt's | N/A |
| Authority | Stale epoch, disabled or tombstoned Account | `denied`; nothing written | N/A |
| Hidden | Foreign, unknown, deleted or tombstoned Project or Job | `unavailable` for every command and the read; nothing written | N/A |

| Immutability | Update or truncate a Job, step or command; change an identity column | Refused; delete (purge) allowed | N/A |

**Acceptance Criteria:**
- Given the same logical step requested by two commands, when both run, then one StepExecution and one ExternalOperation exist, the second returns the original receipt, and the same command ID with a different payload is rejected.
- Given a failed attempt with a potentially chargeable operation, when the user requests a retry, then a new attempt under the same Job exists and cannot start until the prior operation is terminal or reconciled, and no attempt number, third attempt or command bypasses the wait.
- Given any Job, when its state is read, then the public state, stage and reason agree with the stored records, and a terminal attempt can never be started, extended or changed.
- Given a disabled Account, a stale epoch, a foreign, deleted or tombstoned Project, or a browser role, when any command or read is attempted, then nothing is written or revealed.

## Spec Change Log

## Design Notes

The Job has no state of its own: its state is its highest attempt's, so the state, stage and reason cannot disagree with the records. The retry wait lives at the one transition that could bypass it (`waiting→running`) and is computed over every earlier attempt, so a new attempt number gains nothing. A late outcome for an ended attempt is still recorded, because that is how an ambiguous charge is reconciled.

```
attempt 1 failed, step "search" op 1 dispatched   -> request_retry: attempt 2 waiting / awaiting_reconciliation
move_attempt(2, running)                          -> blocked
op 1 dispatched -> ambiguous -> settled           -> read_job: waiting / awaiting_dispatch; move_attempt(2, running) -> moved
```
