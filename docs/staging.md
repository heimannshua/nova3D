# Pushing to staging by hand

Since Story 1.9 a push to the `staging` branch migrates the staging database, checks its Auth settings and asks Vercel for a deployment ("The staging pipeline", below). The first time, and whenever the pipeline cannot be used, the staging database and its Auth settings are changed by hand with the Supabase CLI: steps 1 to 6 are that procedure, and the sections after them are the pipeline, the schedules, the worker images and the hosted checks of Story 1.9. It is written for Josh on Windows: every command is PowerShell (Windows PowerShell 5.1 or PowerShell 7), nothing needs a bash shell, and no command uses `&&`, `export` or a `\` line continuation.

**Do the whole procedure in ONE PowerShell window.** `$ref`, `$work` and the environment variables below live only in the window that set them; a new window starts without them. If you have to close it half way, open a new one, repeat "Before you start", step 2, and re-create the scratch copy of step 3 before you go on.

**Three workflows touch a hosted service, and only two of them change a database.** `.github/workflows/staging.yml` runs on a push to the `staging` branch (it migrates the staging database, checks its Auth settings against `supabase/config.toml` and asks Vercel for a deployment), and `.github/workflows/production-migrate.yml` runs only when you dispatch it by hand (it stops at its first step until a production project exists). `.github/workflows/workers.yml` pushes worker images to GitHub Container Registry on a push to `staging` that changes `workers/` and deploys nothing. Beyond the workflows, only commands that **you** run change a hosted service: the seed (`scripts/seed-accounts.mjs`, which writes rows to the hosted database and asks for `--confirm`), `scripts/schedules.mjs apply` (which creates, corrects, resumes and deletes QStash schedules, asks for `--confirm`, and never touches the database) and the Supabase CLI commands of this page. Nothing else does: not the build, not `npm test`, not `ci.yml` (it runs on every push and touches only the local stack). The Vercel build only *checks* the database (`prebuild` runs `check-env --deployment`, whose accounts API preflight reads at most one row of each table the gate depends on and writes nothing). A deploy therefore fails with one line if a migration is missing; it never fixes it. Migrations, then settings, then seeding the accounts, then the deploy is the order, and **seeding is always yours**: no workflow seeds anything, so seed before the first push that deploys (step 5).

**Migrations and settings are not enough.** A deployment whose database has been migrated but not *seeded* passes the preflight and then locks everyone out, the Administrator included: the live-Account check lets in only an Account, and a pre-authorization or an invitation code is how an Account starts. Step 5 seeds it; do not skip it.

This procedure has been checked against the Supabase CLI's own help (version 2.120.0, the version CI pins), not against the hosted project: the first real run is also its first test, and so is the first run of the pipeline. That is why every step that changes something shows you what it will change first. If anything on screen is not what a step says, stop and ask before answering `y`.

## Before you start

1. **Check what is outstanding.** The Story 1.4 items in [docs/provisioning.md](provisioning.md) are what this page needs: `supabase-organization-plan` (the project is active, on Pro, in the region the ledger records), `supabase-cli-credentials` (an access token, the database password and the project reference), `github-staging-environment` and `vercel-staging-project`. From the repository root:

   ```powershell
   npm run check:provisioning -- --story 1-4 --env staging
   ```

   It names every item due by Story 1.4 that is still missing, and prints no value. Story 1.11 adds one more, `hosted-step-up-and-invitation-check`, which is the hosted check of step 6 below (`--story 1-11 --env staging` lists it); it is due after this procedure, so it is not a prerequisite of it.
2. **Sign in, and give this window what it needs.** `supabase --version` should print 2.120.0 or newer. Nothing secret is typed where it would be shown on the screen or kept in the window's history:
   - The **access token** is the CLI's own business. `supabase login` opens your browser and the CLI keeps the token itself; you never put it in a command line, a file or an environment variable.
   - The **database password** goes to the CLI in an environment variable, read with `-AsSecureString` (the characters are not shown) and converted in this session only. If you leave these two lines out, the CLI asks for the password itself, with the characters hidden, each time it needs it.
   - `$ref` is the project reference from the staging project's General settings (20 lowercase letters, not a secret).

   ```powershell
   supabase login
   $ref = 'the-20-letter-staging-project-reference'
   $securePassword = Read-Host 'Staging database password' -AsSecureString
   $env:SUPABASE_DB_PASSWORD = [System.Net.NetworkCredential]::new('', $securePassword).Password
   ```

   Take the password from your password manager. The staging database password is not the access token.
3. **Be on the commit you mean to deploy.** From the repository root, on `main`, with nothing uncommitted:

   ```powershell
   git status
   git log -1 --oneline
   ```

   The migrations pushed below are the ones in `supabase/migrations/` at this commit. The CLI applies exactly those files, so the commit decides what staging gets.
4. **Never** run `supabase db reset --linked` (it resets the hosted database and runs `supabase/seed.sql`, which would put a `local` identity row into it), and never pass `--include-seed` or `--include-roles` to `db push` (the seed is local-only; the hosted identity row is inserted once by hand, `docs/deployment-setup.md`, Provisioning staging, step 1). Do not edit a migration that any hosted project has already applied: add a new one.

## 1. Link the project and see what is pending

```powershell
supabase link --project-ref $ref
supabase migration list --linked
supabase db push --linked --dry-run
```

`link` takes the database password from `SUPABASE_DB_PASSWORD` (it asks for it, hidden, if the variable is not set) and records the project in `supabase/.temp/` (git-ignored). `migration list` has a Local column and a Remote column: a version in Local and not in Remote is pending. `db push --dry-run` prints the migrations it *would* apply and applies none. Check that the pending list is exactly the migrations you expect from the table below, no more and no fewer, and that they are in this order.

## 3. Auth settings and the exposed schemas (`supabase/config.toml`)

`supabase/config.toml` is the reference for the hosted Auth settings (Google only, sign-ups on, the 30-day time-box and 7-day inactivity timeout, the Before User Created hook) and for the exposed schemas (`public`, `graphql_public`, `lifecycle`, `api`; never `identity` or `projects`). `supabase config push` writes the properties the file declares to the project, and shows the exact diff before it writes each resource.

**Do not push the file as it is.** It is the local file: its `site_url` and `additional_redirect_urls` are loopback addresses, and a hosted project must never hold a `127.0.0.1`, `localhost` or LAN callback (`docs/auth-setup.md`, Staging and production). So push from a scratch copy that carries the hosted addresses, and leave the repository's file alone:

```powershell
$work = Join-Path $env:TEMP 'nova3d-staging-config'
Remove-Item -Recurse -Force $work -ErrorAction SilentlyContinue
New-Item -ItemType Directory -Path (Join-Path $work 'supabase') | Out-Null
Copy-Item supabase/config.toml (Join-Path $work 'supabase/config.toml')
notepad (Join-Path $work 'supabase/config.toml')
```

**The copy is `config.toml` alone, and that is enough.** The only line in the file that names another file is `[db.seed] sql_paths = ["./seed.sql"]`, which `db reset` and `db push --include-seed` read (both of which this page forbids) and `config push` does not. The CLI loads such a copy with no `seed.sql` beside it (checked with `supabase status --workdir` on a copy of the file); if a later change to `config.toml` adds a template, a function or another path and `config push` complains about a missing file, copy that file into the scratch folder at the same relative path. A test fails when the file gains a path other than the seed's, so this paragraph cannot go stale unnoticed.

In the copy, and only there, change:

- `site_url` to `https://<deployment-domain>` (the staging Vercel domain);
- `additional_redirect_urls` to `["https://<deployment-domain>/auth/callback"]` and nothing else.

The Google client is the *staging* client (one client per environment; never reuse another environment's). `config.toml` names it by variable, so give the two variables to this window and not to a file. The client ID is not a secret; the client secret is read hidden, like the password:

```powershell
$env:SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID = Read-Host 'Staging Google client ID'
$secureGoogleSecret = Read-Host 'Staging Google client secret' -AsSecureString
$env:SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET = [System.Net.NetworkCredential]::new('', $secureGoogleSecret).Password
```

Then read before you write:

```powershell
supabase config diff --workdir $work --project-ref $ref
```

It is read-only. What you should see: Auth provider settings, the session limits, the hook, the exposed schemas and the redirect URL. What must **not** appear as a change you did not intend: Email or Phone sign-in switched on, sign-ups switched off, a loopback URL, a different Google client. Local-only sections (`[db.seed]`, `[studio]`, the ports) are not hosted settings and are not pushed. When the diff is what you meant:

```powershell
supabase config push --workdir $work --project-ref $ref
```

It asks `y` or `n` for each changed resource, with its diff; answer each on its own. The hook (`api.before_user_created`) can only be switched on after `20261010120100_api.sql` of step 2 has been applied, because that is the migration that creates the function. Then check that the push took, by asking for the difference again. The second diff must show **no differences**, and `--exit-code` makes the command say so (exit code 0; 2 means a difference is left):

```powershell
supabase config diff --workdir $work --project-ref $ref --exit-code
$LASTEXITCODE
```

If a difference is left, read it: it names a setting the push did not take (a paid-plan feature the project's plan does not include, for example). Fix it before you go on. **Keep the scratch copy until the end of the procedure** ("When you are done"): you may need it again.

Storage needs nothing pushed: Supabase ships no policy on `storage.objects`, so a browser role is denied by default, and `tests/integration/isolation.test.ts` pins that. The 100 MiB file limit in `[storage]` is a hosted setting that the plan must allow (`supabase-organization-plan`).

## 4. Check the database from the application's side

This is the same read-only preflight the Vercel build runs, and it needs the `api` schema exposed, which step 3 did. It needs `.env.staging` (git-ignored; start from `.env.staging.example`, and see [docs/secrets.md](secrets.md) and `docs/deployment-setup.md` for where each value comes from) with the staging URL, the service-role key, `APP_ENV=staging` and `INSTANCE_ID` (the identity row exists, inserted once by hand after the first migration, and `INSTANCE_ID` is the UUID it returned). It validates the same variables the server and the Vercel build need, so since Story 1.6 `.env.staging` must also hold the three keys and settings of Administrator recovery, the same values as in the Vercel Production scope: `RECOVERY_HASH_KEY` (a third hashing key, different from the other two), `RESEND_API_KEY` (the Resend key; the sender is `resend.dev`) and `APP_ORIGIN` (the https origin of the staging deployment, a plain origin with no path; not a secret). A preview deployment holds neither key (`docs/deployment-setup.md`).

```powershell
node --env-file=.env.staging scripts/check-env.mjs --live
```

It must end with `Environment validation passed for staging`, naming the identity row and the accounts API. A one-line failure names what is wrong: the `api` schema is not exposed (step 3), a migration is not applied, a privilege on an `auth` table is missing, or the key is wrong. **A pass does not mean the deployment can be used**: it does not look at who may sign in. That is the next step.

## 5. Seed the accounts

The migrations create the tables; nobody can sign in until an address is pre-authorized or has a code. With `.env.staging` holding `ADMINISTRATOR_EMAIL`, `SEED_ACCOUNT_EMAILS` (set it deliberately; the template leaves it commented out) and the hashing keys (`docs/deployment-setup.md`, Provisioning staging, steps 4 and 5; the audited seed command needs only the one it uses, and, since Story 1.6, neither `RESEND_API_KEY` nor `APP_ORIGIN`):

```powershell
node --env-file=.env.staging scripts/seed-accounts.mjs preauthorize --confirm staging
node --env-file=.env.staging scripts/seed-accounts.mjs list --confirm staging
```

`preauthorize` pre-authorizes the Administrator and every address in `SEED_ACCOUNT_EMAILS`; it is safe to repeat and reports `already pre-authorized` for an address that is, so it also shows what is seeded. `list` shows the invitations issued so far (never a code). **Seed every address that is allowed in today before you deploy**, or those people see the registration screen and nothing else. Every command is audited. `docs/deployment-setup.md` (Provisioning staging, step 5) and `docs/auth-setup.md` (Accounts, invitations and the seed command) have the rest.

## 6. Deploy, then verify

Only now promote the branch (`docs/deployment-setup.md`, Promoting to staging):

```powershell
git push origin main:staging
```

Never force-push `staging`. Once the pipeline is set up ("The staging pipeline", below) this push is also what runs it: it applies whatever is still pending (nothing, after steps 1 to 5), checks the settings and asks Vercel for a deployment. Then open the app with a real Google sign-in and run the hosted checks that belong to the stories you just shipped; each is written where its feature is described:

- sign-in, sign-out and "sign out my other sessions": `docs/auth-setup.md`, Cutting over to session grants (the first real sign-in is the first time the callback runs against hosted Auth);
- the step-up: `docs/auth-setup.md`, Verifying the step-up on hosted Auth (it starts from the Administrator's invitation page now);
- the Administrator's invitation page (Story 1.11): `docs/auth-setup.md`, Verifying invitation management on hosted environments. It needs the Administrator's own Google account, the step-up above and a throwaway account to register with a code; when it passes, record it as the ledger item `hosted-step-up-and-invitation-check` (see [docs/provisioning.md](provisioning.md));
- the Administrator's Accounts page (Story 1.5): `docs/auth-setup.md`, Verifying account administration on hosted environments. It needs the Administrator's own Google account, the step-up above and a throwaway account that registered with a named code, to disable and re-enable; the migration `20261012130000_account_administration.sql` (step 2) must be applied before the deploy, and step 4's preflight now also fails with one line if the database owner cannot delete from `auth.sessions`. When it passes, record it as the ledger item `hosted-account-disable-check` (see [docs/provisioning.md](provisioning.md));

## The staging pipeline (Story 1.9)

`.github/workflows/staging.yml` runs on every push to the `staging` branch, and on nothing else. It uses the `staging` GitHub environment (see `github-staging-environment`), so its secrets are read only by that workflow and only from that branch. In order, it:

1. links the staging project (`supabase link`);
2. applies the migrations in `supabase/migrations/` at that commit (`supabase db push`; never the seed, never roles);
3. writes the scratch copy of `supabase/config.toml` with `node scripts/staging-config.mjs` (the same copy that step 3 above makes by hand: `site_url` is `STAGING_SITE_URL` and the one callback is `<that origin>/auth/callback`; the committed file stays loopback);
4. runs `supabase config diff` against that copy with `--exit-code`, which fails the run when the live Auth settings differ from the file: a provider enabled, the sign-up setting, the redirect URLs or the one-time-code expiry;
5. posts to the Vercel deploy hook, so that **a deployment always follows the migration**. Vercel's own Git build starts when the branch moves and can reach its `prebuild` preflight before the migration lands, and then fail with one line. Asking again, after the database is current, repairs that. This step runs even when the settings check failed (the run still ends red), and not when the migration did not succeed.

Runs of this workflow never overlap (they share one concurrency group, with `cancel-in-progress: false`), and a run that is migrating is never cancelled half way. GitHub keeps at most ONE run waiting in a group: if a run is going and a second is waiting when a third push arrives, the waiting one is dropped and only the newest push runs next. Nothing is lost by that, because `supabase db push` is cumulative (it applies every migration of the checkout that is not applied yet, in order, so the newest run applies what the dropped one would have) and the deploy hook asks for the branch as it is then. The workflow is not a way to seed the accounts, to change a Vercel variable or to create a project: those stay yours.

**What the `staging` GitHub environment must hold** (names only; the values are yours, and `docs/secrets.md` says where each comes from): the secrets `SUPABASE_ACCESS_TOKEN`, `SUPABASE_DB_PASSWORD` and `SUPABASE_PROJECT_REF` (`supabase-cli-credentials`), `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID` and `SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET` (the staging Google client; `config diff` needs both), `STAGING_SITE_URL` (the https origin of the staging deployment: no path, no port; the script refuses anything else, a loopback or local address included. It is not secret in nature, and it is stored as a secret of the environment like every other input of the workflow, so that the workflow file reads only `${{ secrets.NAME }}` and holds no literal) and `VERCEL_STAGING_DEPLOY_HOOK` (the deploy hook of the staging Vercel project, made for the `staging` branch in its Git settings; Vercel documents that anyone who has the URL can deploy the project, so it is a secret: `vercel-deploy-hook`). The check `npm run check:provisioning -- --story 1-9 --env staging` lists what is still missing.

**Production.** `.github/workflows/production-migrate.yml` is the only way a migration reaches a production project, and it has `workflow_dispatch` as its only trigger, in the `production` GitHub environment, with the production `INSTANCE_ID` typed in. Until the production project exists (Story 8.7) it stops at its first step with a message saying so and changes nothing. Even then it applies migrations only: no seed, no settings, no deployment.

## Schedules (Story 1.9)

Periodic work is fired by QStash schedules, never by Vercel cron. Each schedule calls `POST /api/jobs` on the staging deployment with a signed body naming a registered task and this environment's `INSTANCE_ID`; the application checks the signature, the environment and the schedule and message IDs, claims the run, runs the task and writes an immutable receipt. `lib/schedules.ts` is the registry (today: `dormant-identity-purge` daily at 03:00 UTC, `ledger-relay` every five minutes, since Story 1.12 `staging-cleanup` hourly and since Story 1.13 `alarm-monitor` every five minutes, all UTC; every entry also carries its interval in seconds, which the alarm condition `task-late` reads); later stories add theirs there. **After a deploy that adds a task, run `apply`** (below): the new schedule does not exist until you do.

The route checks in this order, and each check stops everything after it, so a foreign or invalid call runs nothing and writes no receipt: the method (405); the two signing keys being set (503); a signature header being present (401: a call with none is refused before its body is read); then the raw body is read, up to 1 KB, because the signature is over those bytes, and a body over the cap, a `content-length` that is not a number or is over the cap, or a body that is not UTF-8 or cannot be read to its end is a **400 even though no signature was checked**; the signature over those bytes with the current key and then the next (401); the shape of the body and the message and schedule IDs (400); the instance (403, or 503 when the database does not answer); the claim; the run. QStash retries every answer outside 200 to 299, a 4xx included, so a refused call is refused again on each retry and writes nothing each time (only a 489 with `Upstash-NonRetryable-Error: true` stops it, which the route does not send: the story fixes the statuses).

The QStash names (`QSTASH_URL`, `QSTASH_TOKEN`, `QSTASH_CURRENT_SIGNING_KEY` and `QSTASH_NEXT_SIGNING_KEY`) are set in the staging Vercel project's Production scope and in `.env.staging`, and **never in a preview**: the environment check rejects them there. They are not on the list of variables a hosted deployment must hold, because the route answers 503 without them (and `/api/health` is unchanged). With the QStash region in `QSTASH_URL` set explicitly (us-east-1: the SDK's default is the EU), make the live schedules equal the registry from `.env.staging`, which needs `QSTASH_URL`, `QSTASH_TOKEN`, `APP_ORIGIN` and `INSTANCE_ID`:

```powershell
node --env-file=.env.staging scripts/schedules.mjs list
node --env-file=.env.staging scripts/schedules.mjs check
node --env-file=.env.staging scripts/schedules.mjs apply --confirm staging
```

`list` prints the registry and makes no network call. `check` compares the live schedules with it and exits 1, naming each difference, when they differ (a schedule missing, one extra, another cron expression, another destination or body). `apply` makes them equal (it creates what is missing, corrects what differs in place, resumes a paused schedule and deletes one that repeats a task or is not in the registry) and refuses to run without `--confirm staging`, the name of the environment in `APP_ENV`; it sets no retry, delay or other delivery setting, which stay the account's. The settings come from `.env.staging`: `QSTASH_URL`, `QSTASH_TOKEN`, `APP_ORIGIN`, `INSTANCE_ID` and `APP_ENV=staging`. An operator runs them (you, from your own machine), after the deploy that contains the route and whenever the registry changes; CI never does, because it holds no QStash token. Run `check` after `apply`: it must exit 0.

## Worker images (Story 1.9)

`.github/workflows/workers.yml` runs on a push to `staging` that changes anything under `workers/`, or one of the files an image copies in and installs from (`lib/service-signing.ts`, `lib/canonical-json.ts`, `package.json`, `package-lock.json` and `.dockerignore`), so the gateway's image is rebuilt when what it bakes in changes. `scripts/ci/list-workers.mjs` finds each `workers/<name>/Dockerfile`; the first worker is the file gateway (`workers/files`, Story 1.12, "The file gateway" below), the second is the heartbeat task (`workers/heartbeat`, Story 1.13, "Operational alarms" below), and the others arrive with Story 2.7. A worker is built from the **repository root** (the build context is `.`, with `-f workers/<name>/Dockerfile`), because the workers share modules of `lib/` with the application (the gateway two, the heartbeat task one) and install from the one root lockfile; the root `.dockerignore` keeps the context to what the image copies. For each worker it builds the image, pushes it to GitHub Container Registry (the `GHCR_TOKEN` secret of the `staging` environment) and writes the image's **digest** to the run's summary: `ghcr.io/<owner>/<repository>/<worker>@sha256:...`. A digest is deployed, never a tag, and older images stay in the registry because reproducible Versions need them.

**The deploy to Railway is a manual step.** The pipeline was meant to deploy that digest to Railway with the project token (`RAILWAY_TOKEN`), but Railway's public API reference documents no call that points an existing service at an image digest with a project token (it documents `serviceInstanceUpdate` for settings such as the start command, `serviceInstanceDeploy` and `deploymentRedeploy` for deploying what is already configured, `serviceCreate` with an image only for a new service, and the CLI's `railway redeploy`, which redeploys the same tag). A call written from memory is not allowed here, so this is the one item of the story that stopped to ask: until Railway documents it (or you approve a way), copy the reference from the summary, set the worker service's image to it in the Railway project and deploy it, and keep one version of each worker running at a time. The worker registry of Story 2.7 records the digests.

## The file gateway (Story 1.12)

Private files move through one place: `workers/files`, a Node service on Railway that checks the Account again, live, before every chunk of at most 1 MiB. No file passes through a Vercel function, and the application never holds a storage credential. The contract is in `docs/authority-contract.md` ("The file gateway"); this is what you set up.

**What it needs, by name** (the values are yours; `docs/secrets.md` says where each comes from, and the ledger items `gateway-database-role`, `gateway-storage-s3-key` and `railway-files-service` track them):

- In the **Railway gateway service**: `APP_ENV`, `INSTANCE_ID` and `APP_ORIGIN` (the staging https origin: the one origin that may call the gateway from a browser), `SERVICE_KEYS_APPLICATION` (the application's public key set: not secret), `GATEWAY_DATABASE_URL` (secret; with `?sslmode=require`), `GATEWAY_STORAGE_S3_ENDPOINT` and `GATEWAY_STORAGE_S3_REGION` (not secret), `GATEWAY_STORAGE_S3_ACCESS_KEY_ID` and `GATEWAY_STORAGE_S3_SECRET_ACCESS_KEY` (secret). Railway sets `PORT`. The service exits at start-up, before it listens and with a message that names the variable, when anything is missing, and when the database it is pointed at is not the environment `APP_ENV` and `INSTANCE_ID` name.
- In the **staging Vercel project's Production scope** (never a preview, which the environment check rejects): `SERVICE_SIGNING_KEY_APPLICATION` (the private half of the application's key: secret), `SERVICE_KEYS_APPLICATION` and `FILE_GATEWAY_URL` (the gateway's https origin). None is required for the application to run: without them the ticket route answers 503 and the staging cleanup records `no_store`.

**The database role has no password until you give it one.** The migration creates `nova3d_gateway` without one, because a password in a migration is a secret in the repository. In the Supabase dashboard's SQL editor, as the database owner, run `alter role nova3d_gateway with password` followed by a long random password from your password manager, in quotes. Then build the connection string for the pooler in transaction mode (the user is `nova3d_gateway.<project-ref>`), end it with `?sslmode=require` (or `verify-ca` or `verify-full`: the gateway exits at start-up, naming the variable, for staging or production when the URL does not ask for TLS) and store it as `GATEWAY_DATABASE_URL` in the Railway service. The gateway uses no session state and no named prepared statements, so the transaction-mode pooler is the right one; local and CI have no pooler and use the direct connection, which is why the hosted path is a check of yours (`hosted-gateway-check`).

**The image.** A push to `staging` that changes anything under `workers/`, or what the image copies in (above), builds `workers/files` and prints its digest in the run's summary ("Worker images", above). Create or update the `files` service from that digest by hand, give it a public domain and the health check path `/healthz`, and keep one version of it running. The image runs as a non-root user and listens on `PORT`. On `SIGTERM` (what a redeploy sends) the gateway stops accepting connections and lets the requests in flight finish for up to ten seconds, then cuts what is still running and exits, so a deploy no longer ends every transfer at once; an upload or a download that needs longer than that restarts with a new ticket, as after any interruption.

**Rotating the application's key, and compromise.** Add a new key as the active one and keep the old as the single retiring key with an `until` six minutes ahead; set the key set in the gateway first and in the application with the new private key afterwards; remove the retiring key when its `until` has passed (`docs/secrets.md`). On suspected compromise, revoke the key in the SQL editor with `select * from api.revoke_service_key('application', '<key ID>', 'compromise')`, which also ends every staging lease and transfer handle opened under it, and then rotate: a ticket signed by a revoked key is refused at once, whatever its time.

**The hourly cleanup.** `staging-cleanup` is in the schedule registry ("Schedules", above): run `node --env-file=.env.staging scripts/schedules.mjs check` and then `apply --confirm staging` after the deploy that contains it. Each hour the application asks `api.list_expired_staging` for up to 50 leases that are expired or released, and sends the gateway one signed `delete-staging` command for each; the gateway re-checks in one statement that the lease is still expired or released, so a lease renewed in the meantime is kept. With no gateway configured the run is `no_store` and nothing is read or deleted; a gateway that is down fails the run, and QStash retries it.

**Running it locally.** `node scripts/setup-env.mjs local` writes the application's signing key pair, the gateway's database role and Storage key pair and the gateway's address to `.env.local` from the running stack. Start the gateway beside the application with its own `APP_ORIGIN`, for example `APP_ORIGIN=http://127.0.0.1:3000 node --env-file=.env.local workers/files/src/main.ts`, and build the image with `docker build -f workers/files/Dockerfile -t nova3d-files .`. The browser tests start their own gateway (`playwright.config.ts`).

## Operational alarms (Story 1.13)

Nothing used to tell the Administrator when something stopped. Now an alarm is a record (`lifecycle.alarms`) that is opened when a condition holds and resolved, with the record kept, when it stops holding; the Administrator is emailed through the one mailer of Story 1.6 (Resend in staging, from the `resend.dev` sender, to `ADMINISTRATOR_EMAIL` and to nobody else; the Resend account must be registered with that address), and the open alarms are listed on the Operations page of the Administration area (`/admin/operations`: read-only, 404 for anyone but the Administrator; no acknowledge, snooze or delete). The email holds fixed words, the environment (`APP_ENV`, in the subject line as `[staging]`, because staging and production share one Administrator address), the condition, the subject, the first time (UTC), every whole number and yes/no value of the alarm's detail with its name (the age in seconds, the count of events pending) and the last receipt of the task: never an address, a title, a code, a token or anything private. The page lists the same numbers on each open alarm's card.

**The monitor.** `alarm-monitor` is a task in the schedule registry, fired every five minutes by QStash like the others (`lib/schedules.ts`). Each run reads the observations the database reports (every age in seconds, on the database's clock: the application never compares its clock with the database's), evaluates the conditions below, raises an alarm for each finding (a second finding for a condition that is already open refreshes its record and sends nothing new), resolves the open alarms of its conditions that no longer hold, and emails the alarms that are due. Its receipt holds counts only: `raised`, `resolved`, `mailed` and `mail_failed`. A condition that cannot be evaluated because the database does not answer leaves its alarms as they are and fails the run, which QStash retries. A condition whose own precondition is missing now is **unobservable** (below): it raises nothing and resolves nothing. **Run `scripts/schedules.mjs apply` after the deploy that contains it** ("Schedules", above): until the `alarm-monitor` schedule exists nothing evaluates the conditions.

| Condition | Subject | Evaluated by | Raised when |
| --- | --- | --- | --- |
| `task-late` | the task | the monitor | a task's latest finished receipt is older than twice its interval (`ledger-relay` 10 minutes, `staging-cleanup` 2 hours, `dormant-identity-purge` 48 hours); a task that never finished one is measured from the first receipt of any task. The monitor is left out: it is what evaluates this |
| `ledger-pending` | none | the monitor | the oldest pending ledger event is over 15 minutes old, unless the relay's latest finished receipt is `no_store` (with no ledger store the events can never be relayed; the store is Story 8.9's): then it is unobservable, so nothing opens and an alarm that is already open stays open |
| `identities-unaccounted` | none | the monitor | more than 25 Auth identities have no Account |
| `heartbeat-stale` | none | the monitor; unobservable when `SERVICE_KEYS_HEARTBEAT` is unset | the latest heartbeat is older than 2 hours, or there is none while the first receipt of any task is older than that |
| `qstash-stale` | none | the application, when a heartbeat arrives | the latest receipt of any scheduler task is older than 2 hours, or there is none while the first heartbeat is older than that |
| `monitor-late` | none | the application, when a heartbeat arrives | the latest finished `alarm-monitor` receipt is older than 10 minutes (twice its interval), or there is none while the first receipt of any task is older than that. A missing or dead `alarm-monitor` schedule is therefore reported within about 40 minutes, when the next Railway heartbeat arrives after the monitor has been silent for 10 minutes. `task-late` still leaves the monitor out |

**The email rule** is the database's (`api.alarms_due_mail`): an open alarm is due when it has had no `sent` notice in the last 24 hours and, for an alarm with no subject, no `sent` notice for any alarm of the same condition in the last 24 hours. So a subject-keyed alarm is emailed at the evaluation that raised it; a threshold alarm is emailed when it opens, unless its condition was emailed within 24 hours (then when that window ends, if it is still open); and an alarm that stays open is reminded at most once every 24 hours. **An alarm is claimed before its mail is sent:** `api.alarms_due_mail` takes one lock and records a `claimed` notice for each alarm it hands out, in the same transaction, so the monitor and the heartbeat evaluation (both can run at :00 and :30) never send the same alarm twice. A claim holds its alarm, and for an alarm with no subject its whole condition, for 10 minutes, unless a later `sent`, `failed` or `unknown` notice for that alarm exists. The sender then records what happened: `sent` closes the 24-hour window; `failed` (the provider refused) and `unknown` (it did not answer; the mail may have gone out, so one duplicate is accepted) close no window and release the claim, so the mail is retried at the next evaluation; the alarm is on the page meanwhile. An alarm that was claimed but whose outcome was never recorded (the run was cut off, the ten-second start deadline passed before it, or the notice could not be written) keeps its claim and is emailed again at the first evaluation more than 10 minutes after the claim. A resolved alarm is never emailed. Alarm history is kept for ever in this story.

**Unobservable conditions, and removing one on purpose.** A condition whose own precondition is missing now answers *unobservable*: the monitor and the heartbeat evaluation raise nothing and resolve nothing for it, so an alarm that is already open stays open until the condition can be observed again and is found clear. Today that is `ledger-pending` while the relay's latest finished receipt is `no_store`, and `heartbeat-stale` while `SERVICE_KEYS_HEARTBEAT` is unset. If you remove such a condition on purpose (you retire the heartbeat service and unset `SERVICE_KEYS_HEARTBEAT`, or the ledger store is gone for good) and its alarm is open, nothing will ever close it; close it yourself in the Supabase SQL editor as the database owner with `select * from api.resolve_alarm('<condition>', null)`, for example `select * from api.resolve_alarm('heartbeat-stale', null)`. An alarm that has a subject needs it too: `select * from api.resolve_alarm('<condition>', '<subject>')`. Use it only for a condition you have removed on purpose: for one that is still in force the monitor raises a new alarm, and emails it, at the next evaluation.

**The two schedulers watch each other.** The monitor runs on QStash, so it cannot see QStash stop. The heartbeat task (`workers/heartbeat`), a cron job on Railway, signs one heartbeat every 30 minutes and posts it to `POST /api/heartbeat`; the application records it, evaluates `qstash-stale` and `monitor-late`, emails what is due and answers how old the latest scheduler receipt is. If the heartbeat stops, the monitor raises `heartbeat-stale`; if QStash stops, the heartbeat raises `qstash-stale`; and if the monitor alone stops (its schedule was never created, or was deleted or paused), the next heartbeat raises `monitor-late`, within about 40 minutes. The route is a machine path like `/api/jobs` (no cookie, no CSRF token, no browser Origin; the signed token is the only authentication). It answers 200 `{"state":"recorded","receipt_age_seconds":n}`, 401 `{"error":"invalid_token"}` (one body for every token failure, a revoked key included), 409 `{"state":"duplicate"}` for a token already used, 403 when an `Origin` header is present, 400 for a body over 16 bytes, and 503 when `SERVICE_KEYS_HEARTBEAT` is unset or unusable, or the database does not answer the record, the observations, the alarm records or the list of what is due (never a 200 that skipped the evaluation; a mail the provider refuses is counted and retried at the next evaluation, one whose notice cannot be recorded is retried once its claim lapses after 10 minutes, and the answer is still 200). **Methods.** The route file exports `POST` only, so Next.js answers every other method itself, before the route runs: `OPTIONS` gets a `204` with `Allow: OPTIONS, POST`, and `GET`, `HEAD`, `PUT`, `PATCH` and `DELETE` get Next.js's own `405` (no body, no `Allow`, and no `cache-control: no-store`, which the route's own answers all carry, as `/api/jobs` is). The `405` that `lib/heartbeat.ts` itself holds (`Allow: POST`, no-store) answers only a direct call of the handler, which is what its unit tests pin; it is not what a request over HTTP meets. Every answer the route itself gives is no-store.

**The heartbeat service (Railway; tracked by `railway-heartbeat-service`).** Build the image with the pipeline like the gateway's ("Worker images", above: a push to `staging` that changes anything under `workers/` builds `workers/heartbeat` and prints its digest). Create a `heartbeat` service in the Railway project from that digest, give it **no public domain and no health check** (it listens on nothing), and set its **cron schedule to `*/30 * * * *`** (Railway's Cron Schedule setting of the service; it is set by hand, like the image). It holds exactly five variables: `APP_ENV` (`staging`), `INSTANCE_ID` (the staging instance), `APP_ORIGIN` (the staging https origin it posts to), `SERVICE_KEYS_HEARTBEAT` (the public key set, not secret) and `SERVICE_SIGNING_KEY_HEARTBEAT` (its own private key, secret). It holds no database access and no Storage key. Each run prints one line and exits: 0 and `The heartbeat was recorded.` when the application answered 200, 1 and `The heartbeat was not accepted.` (or `could not be sent`) for anything else, so Railway marks a refused run as failed; with a variable missing or malformed it exits 1 before sending anything and lists the variable's name, never its value.

Make the key pair on your own machine with the one-liner in `docs/secrets.md` ("Service-signing keys"). Keep the private half (the base64 PKCS#8 text) only in the password manager and the Railway service as `SERVICE_SIGNING_KEY_HEARTBEAT`. The key set is the JSON `{"issuer": "heartbeat", "active": "<key ID>", "retiring": null, "keys": {"<key ID>": "<base64 SPKI public key>"}}` with a key ID you choose, such as `heartbeat-2026-10`; set it as `SERVICE_KEYS_HEARTBEAT` in the Railway service **and** in the staging Vercel project's Production scope (the application verifies with it, and the monitor starts to watch for the heartbeat only once the application has it). It is optional in the application: without it the route answers 503 and `heartbeat-stale` is unobservable (it opens nothing, and closes nothing that is open). The private half is never an application variable, and the environment check rejects it in a preview. Rotation, and revoking a heartbeat key (`api.revoke_service_key('heartbeat', ...)`, after which the route refuses its tokens), are in `docs/secrets.md`.

**What to expect on first setup.** Two things raise an alarm, and an email, on purpose; neither is a fault.

- **Setting `SERVICE_KEYS_HEARTBEAT` in the application** makes the monitor start to watch for the heartbeat. On any database whose scheduler has been running for over two hours, the next monitor run (within about five minutes of the application being redeployed with the key set) raises `heartbeat-stale` and emails it, and it stays open until the first heartbeat arrives. The alarm and its email are expected, and the first successful heartbeat resolves the alarm (at the next monitor run, within five minutes). So create the Railway service first and **trigger one run by hand immediately after setting the key set** (the service's "Run now", or redeploy it): the alarm is then open for a few minutes, or not at all.
- **A task added by a later story** is in the registry from the deploy but has no QStash schedule until `apply` creates it, and the condition `task-late` measures a task that has never finished a run from the first receipt of any task, so it raises `task-late` for that task (and emails it) until its schedule exists and has fired once. Run `node --env-file=.env.staging scripts/schedules.mjs apply --confirm staging` **right after the deploy** that adds a task (the same applies to `alarm-monitor` itself, which is not watched by `task-late`: until its schedule exists nothing evaluates the monitor's conditions, and the next Railway heartbeat, within 30 minutes, raises `monitor-late` and emails it; the first monitor run after `apply` resolves it at the next heartbeat).

The heartbeat task waits thirty seconds for the application's answer. The route records the heartbeat and then evaluates and emails what is due before it answers; it starts no new email after ten seconds, and one email waits at most ten seconds for the provider, so the slowest answer is about twenty seconds. An alarm it did not reach keeps its claim and is emailed at the first evaluation more than ten minutes after the claim.

**Running it locally.** `node scripts/setup-env.mjs local` writes the heartbeat pair to `.env.local` beside the application's. With the application running, `APP_ORIGIN=http://127.0.0.1:3000 node --env-file=.env.local workers/heartbeat/src/main.ts` posts one heartbeat (a second run signs a new token; a token is accepted once). Build the image with `docker build -f workers/heartbeat/Dockerfile -t nova3d-heartbeat .`; with no environment it exits 1 and lists the five names. The browser tests start no heartbeat task: the tests that need one sign a heartbeat themselves.

## Verifying the pipeline, the schedules and the purge (Story 1.9)

Each check is yours, once, on staging. Nothing here creates a Project or reads a person's content.

1. **The pipeline.** The `staging` environment holds the secrets above, `vercel.json` is unchanged (`git.deploymentEnabled.main` is false, and `github.enabled` is not set, which would stop deploy hooks), and `git push origin main:staging` has run the workflow. In the Actions tab the run must show every step green: the link, the migration (nothing pending if steps 1 to 5 already ran), the settings check and the deployment request; and the Vercel dashboard must show a deployment marked as triggered by a deploy hook. Read the settings check's output too: it must show no differences. Record it as `hosted-pipeline-check`.
2. **The schedules.** After the deploy, run `scripts/schedules.mjs check` (it exits 1 and lists both schedules, since none exists yet), then `apply`, then `check` again (exit 0). With the route reachable, an unsigned `POST` must answer **401** with `cache-control: no-store` (the route's own answer), and a `GET` **405** (Next.js's own answer for a method the route does not export: it carries no `cache-control` header). A 503 means the QStash signing keys are not set in the Production scope. The commands print the status line and the headers, so you can see both:

   ```powershell
   $origin = 'https://the-staging-deployment-domain'
   curl.exe --silent --output NUL --dump-header - --request POST "$origin/api/jobs"
   curl.exe --silent --output NUL --dump-header - "$origin/api/jobs"
   ```

   Within five minutes the relay has fired. Read its receipt as the database owner (the Supabase dashboard's SQL editor; the receipts are in a closed table, reached only through the `api` function): `select * from api.last_job_run('ledger-relay')`. Events from Account activity are pending and no ledger store exists until Story 8.9, so the outcome is `no_store` with the pending count (or `idle` when nothing is pending), and the result holds counts only. Firing twice is harmless: a second delivery of one message answers `duplicate` and runs nothing. Record it as `hosted-schedules-check`.
3. **The purge.** After the first 03:00 UTC run, `select * from api.last_job_run('dormant-identity-purge')` must show the outcome `ran` and the counts `deleted`, `kept`, `locked` and `remaining`. An Auth identity that never became an Account and has been idle for 30 days is deleted; an Account's identity cannot be (the foreign key refuses it, and the run counts it as kept). Do not back-date anything on staging: the back-dated cases are covered by the local suite. The Auth identity count is read in the Supabase dashboard before and after, and the difference must equal `deleted`.

If a check fails, the receipt (outcome `failed`, with the class of the error and never its message) and the QStash console's message log say where. A failed run is retried by QStash.

## Verifying the file gateway (Story 1.12)

Each check is yours, once, on staging, with a throwaway Account that is registered with a code and signed in in a browser. Nothing here reads a person's content.

1. **It is up.** With the service running, the gateway answers its health check, and a request from any other origin is refused. The first command prints the status line and the headers, so you can see `cache-control: no-store`; the second must print a 403:

    ```powershell
    $gateway = 'https://the-staging-gateway-domain'
    curl.exe --silent --output NUL --dump-header - "$gateway/healthz"
    curl.exe --silent --output NUL --write-out "%{http_code}" --header "Origin: https://evil.example" "$gateway/healthz"
    ```

2. **A file goes through it.** In the signed-in browser at the application's origin, open the developer console and ask the ticket route for an upload ticket (a POST to `/api/transfers/tickets` with the `x-csrf-token` header read from the `nova3d-csrf` cookie and the body described in `lib/transfer-tickets.ts`), then PUT a few megabytes to `<gateway>/v1/uploads/<id>` with the ticket in `Authorization: Ticket ...`. Expect a 201, then read it back whole and by range with a download ticket for each read. This is also the first time the gateway reaches the database through the pooler in transaction mode, which no local test can show: a 503 that never clears means the connection string, the role's password or the pooler's mode is wrong (the gateway logs only an error's class name).
3. **Access ends while it streams.** Upload a file of about 100 MiB, start downloading it, and disable the Account from the Administrator's Accounts page while it runs: the download stops at a whole number of chunks and the browser reports an interrupted download; a new ticket cannot be issued. Re-enable the Account and use an old ticket: it is refused (the Account is under a newer epoch).
4. **The cleanup.** After the schedule exists and an upload's lease has expired (24 hours without activity), `select * from api.last_job_run('staging-cleanup')` shows a finished receipt: `idle` when nothing was expired, `ran` with `expired`, `deleted` and `kept` counts when something was removed, and never `no_store` once the gateway is configured. Record the checks as `hosted-gateway-check`.

## Verifying the alarms (Story 1.13)

Each check is yours, once, on staging. Nothing here reads a person's content, and the first three leave no open alarm behind.

1. **The monitor runs.** After `apply` has created the `alarm-monitor` schedule (`scripts/schedules.mjs check` exits 0), within five minutes `select * from api.last_job_run('alarm-monitor')` (the Supabase dashboard's SQL editor, as the database owner) shows a finished receipt with the outcome `ran` and the counts `raised`, `resolved`, `mailed` and `mail_failed`. On a healthy staging all four are normally 0 once the first runs have settled.
2. **The heartbeat arrives.** Within 30 minutes of the Railway service being deployed, its run log shows `The heartbeat was recorded.` and the run is marked successful, and `select latest_heartbeat_age, latest_receipt_age from api.alarm_observations()` shows both ages small. Run the service again by hand and it signs a new token and succeeds again; there is no way to replay one.
3. **The mail path works end to end.** In the SQL editor run `select * from api.raise_alarm('hosted-check', null, '{}')`. It is a condition no evaluation looks for, so nothing resolves it: within five minutes the Administrator address receives one email naming the condition `hosted-check`, and the alarm is listed on `/admin/operations` (signed in as the Administrator, on a phone and on a desktop) with its email state showing when it was sent. Then close it with `select * from api.resolve_alarm('hosted-check', null)`: it moves to the resolved list and is never emailed again. If no email comes, the page's email state says "failing" when the provider refused the mail or did not answer (it is retried at every evaluation), and "pending" when none was tried yet; the SQL editor reads the notices too (`select outcome, at from lifecycle.alarm_notices order by at desc limit 5`: the tables are closed to every role but the owner), and the Resend dashboard says why a mail was refused.
4. **Each scheduler is watched by the other** (optional, because it needs two hours; do it once). Pause the Railway cron schedule for a little over two hours: the next monitor run raises `heartbeat-stale` and emails it, and the first heartbeat after you resume it resolves it on the next monitor run. Or pause the QStash schedules for a little over two hours: the next heartbeat raises `qstash-stale` and emails it, and the first receipt after you resume resolves it on that heartbeat. Resume both when you are done.
5. **The monitor is watched too** (optional; it needs about 40 minutes). Pause only the `alarm-monitor` QStash schedule: ten minutes after its last receipt, the next Railway heartbeat (within 30 minutes) raises `monitor-late` and emails it, and the first heartbeat after the monitor has run again resolves it. An environment whose `alarm-monitor` schedule was never created is reported the same way, within about 40 minutes of the scheduler's first receipt. Resume the schedule when you are done.

Record the checks as `hosted-alarm-check`.

## If something goes wrong

Everything here assumes you are still in the window you started in (see the top of the page).

- **A migration fails.** Read the error, then `supabase migration list --linked` to see what the project recorded. A file that is not recorded can be fixed in the repository, committed and pushed again. A file that is recorded is never edited: add a new migration instead.
- **The deploy fails its preflight.** Read the one line; it names the cause. It means the database does not yet match the build, which is what the check is for. Do not skip the check.
- **Nobody can sign in after the deploy.** The accounts were not seeded (step 5), or an address was left out of it. Seed it, and have the person sign in again.
- **You need the previous build back.** Redeploy it from Vercel. Leave the migrations in place: each one is additive and harmless to the previous build, and removing one would delete data. `docs/auth-setup.md` says what each story's rollback means for sessions.
- **You pushed a setting you did not mean to.** The scratch copy from step 3 is still there until you clean up: change the setting in it (or in the dashboard), run the diff again and push again; `config push` only moves what the file declares. If you have already cleaned up or closed the window, repeat "Before you start", step 2, and step 3 from the top to make the copy again.

## When you are done

Remove everything this procedure put in the window, the scratch copy and every secret included, and sign the CLI out on a machine that is not only yours (it asks you to confirm):

```powershell
Remove-Item -Recurse -Force $work
Remove-Item Env:SUPABASE_DB_PASSWORD, Env:SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_ID, Env:SUPABASE_AUTH_EXTERNAL_GOOGLE_CLIENT_SECRET
$securePassword.Dispose()
$secureGoogleSecret.Dispose()
supabase logout
```

Nothing in the scratch copy is a secret (the file holds variable names), but it holds your hosted callback, so it does not stay around. Closing the window also ends every variable in it; this is for the window you keep open.
