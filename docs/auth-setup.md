# Authentication setup

The deployed shell is private and uses Google through Supabase Auth. Signing in with Google is necessary but never enough: every private page needs an active Account and a valid session grant, and an Account exists only for an invited person (a pre-authorized address or a redeemed invitation code). There is no password fallback and no list of allowed addresses in the environment; the interim email-list gate that earlier builds read is gone (Story 1.3 Part B).

Google is the only sign-in credential: the target is Google on, and email, phone and anonymous sign-in off, in every environment. Sign-ups stay on, because turning them off blocks every first-time Google sign-in; the live-Account check is the gate. `supabase/config.toml` declares these settings and applies them to the local stack (an integration test reads them back from the running stack); nothing yet compares them with a hosted project, so staging and production are set by hand until Story 1.9. The one other way back in is Administrator recovery (Story 1.6, below): it mints a session for the Administrator's own Google-backed account through Auth's Admin API and enables no other credential. The settings: `[auth]`, `[auth.email]`, `[auth.sessions]` (30-day time-box, 7-day inactivity timeout, 15-minute OTP expiry) and `[auth.external.google]`.

## How access is decided (Stories 1.3 and 1.4a)

One resolver, `lib/access.ts`, turns the verified session and one call to the database, `api.authorize_session`, into one of seven states, and the proxy, every private page, the sign-in callback and the registration action all ask it. The user always comes from the verified server session (the Auth service is asked, the cookie is not trusted), never from a form field, a header or a claim; the session comes from the `session_id` of the very access token Auth has just verified for that user. `authorize_session(user, session)` answers with the Account state first and then the session's grant (below), so one call replaces the separate Account lookup of Story 1.3.

| State | Meaning | What happens |
| --- | --- | --- |
| `signed-out` | no verified session, or one whose Auth session the database no longer sees | any private path redirects to `/login?error=not_signed_in` ("Sign in with an invited Google account to continue") |
| `session-ended` | a verified session whose grant is not valid: none issued, revoked, issued more than 30 days ago, unused for more than 7 days, or issued under an older epoch than the Account's | any private path redirects to `/login?error=session_ended` ("Your session ended. Sign in again."); the Auth session is left alone, and signing in again issues a new grant |
| `unregistered` | a verified Google identity with no Account | every path except `/register` redirects to `/register` |
| `active` | an active Account and a valid grant | the page renders; `/register` redirects Home |
| `disabled` | the Account is disabled | signed out (every session of the user is ended and the cookies expired) and sent to `/login?error=account_disabled`; no private content |
| `refused` | the Auth user's Google identity is no longer the one pinned to the Account | this session's grant is revoked and audited; signed out everywhere and sent to `/login?error=not_allowed` |
| `unavailable` | Auth or the database could not answer, in time or at all | access is denied and the request goes to `/login?error=auth_unavailable`, whose message offers "Try again"; the session is kept so the person can return when the outage clears |

A deliberate sign-out lands on `/login?notice=signed_out` ("You have been signed out."), shown as a notice, not an alert.

Any error, a timeout or an answer of an unexpected shape is `unavailable` (or `signed-out` when Auth says there is no session), never a pass, and nothing is cached between requests: no JWT, grant or Account answer is honored from memory. The proxy makes one Auth call (plus a read of the stored session) and one `authorize_session` call for each private request, and the page repeats them once (memoized with React `cache()` for the render, so the page and anything inside it share one answer), because the proxy alone is not a boundary. A Server Action asks for itself and never reuses an answer. The calls of one decision share one time budget (5 seconds), the sign-in callback's whole chain another (10 seconds) and a sign-out action's a third (8 seconds), so three slow answers cannot take three times as long. The session ID is taken from the verified token only if its subject is the verified user, it has not expired and it carries a `session_id`; in the sign-in callback it comes from the token the code exchange has just returned.

Route handlers under `app/api` start from `requireApiAccess()` (`lib/auth.ts`), which gives the same JSON answers; Server Actions that need the gate use `withActiveAccount` or `withVerifiedUser` (the sign-out actions). A test fails when a route handler outside the short public list (`/api/health`) does not call `requireApiAccess`. `/login`, `/auth/callback` and `/api/health` stay public, and `/kit` only while synthetic data is on; `/register` is private (it needs a session) and renders without the navigation shell.

**Private `/api` paths answer JSON, never HTML or a redirect.** A denied request gets `401` with `not_signed_in` (no valid session) or `session_ended` (a valid session whose grant has ended), `403` with `account_required` (no Account), `account_disabled` or `not_allowed`, or `503 {"error":"auth_unavailable","retryable":true}` with `Retry-After: 5` when the check could not be made (a 503 rather than 401 or 403, because the person has not been refused; it is retryable). The body never carries a reason beyond that code. A disabled Account or a changed Google identity is signed out on an API request as well.

**Registration** (`/register`) is the only place a signed-in identity without an Account can go. It states that the instance operator administers the hosting accounts that hold users' data, takes an invitation code, and works on phone and desktop in English and Hebrew. A wrong, used, revoked or rate-limited code all give the same generic, localized message and a new command ID; the code is never logged and never sent back. If the database cannot be reached the form shows a retry message, keeps the command ID and keeps what was typed, so the retry is the same command. "Use a different Google account" ends this browser's session and then starts Google again with `prompt=select_account` (and no `login_hint`), so Google shows its account chooser instead of signing the same account straight back in (Story 1.4b). The session is ended first, because ending it also removes this browser's PKCE verifier cookies; the new sign-in is built after that, from a fresh client. If Google cannot be started the person lands on sign-in with the unavailable message, where the ordinary button starts it.

**Pre-authorized addresses** become Accounts in the sign-in callback: right after the code exchange it asks Auth who signed in and calls `api.consume_preauthorization` for that user, and, once the Account is live, issues the grant of that session (see Session grants below). A pre-authorized address becomes an Administrator or member Account at its first verified Google sign-in (the Administrator's Google subject is pinned then), or, for a session that signed in before the address was seeded, the next time that session opens `/register` (the proxy consumes it there, and a refusal signs the person out the same way); the same address under another Google subject, or a disabled Account, is signed out (`not_allowed`, `account_disabled`); an identity with no pre-authorization goes on to `/register`; a failure of any step signs the person out with `auth_unavailable`, on this browser only (an outage says nothing about their other devices), while a refused or disabled identity is signed out everywhere. Every call to Auth or the database in these paths, and every sign-out, has a deadline (5 seconds): a hung service ends in the same fail-closed redirect, never a hung request. A Server Action refused by the proxy (a form left open after the session ended, the Account was disabled, or the Account was created in another tab) is answered with a redirect only; the form then reloads `/register`, and that page request signs out and shows the right sign-in message or Home.

## Session grants (Story 1.4a)

A session grant is the Identity-owned record that this Auth session may use this Account. A valid Google session and an active Account are not enough: the session also needs its grant, which is how one session can be signed out, all the others can be, and a session can end by age or idleness, none of which Auth's own session alone gives the application. The table is `identity.session_grants` (unexposed, row-level security on, no policies, closed to every role); the only callable surface is the `api` schema, executable by the service role alone.

- **One grant per Auth session**, keyed by Auth's `session_id`, which the server takes from the verified access token and never from a client. It records the Account, the Account's authorization epoch at issue, when it was issued, when it was last used, and, if it has ended, when, by whom and why.
- **Issued** (`api.issue_grant`) whenever a signed-in session becomes an active Account's: at the end of the sign-in callback, when a session that signed in before its address was seeded claims its pre-authorization at `/register`, and at registration with a code (and, since Story 1.4b, inside `api.complete_step_up` when a step-up is accepted, so the new session gets its grant in the same transaction as its marker). It is idempotent (a repeat changes nothing and audits nothing more), never revives a revoked grant, and refuses a session Auth does not have for that user, a disabled Account, and a Google identity that is not the pinned one. If a session already has a grant that is revoked, expired, idle or stale, it says which instead of "exists". If it cannot be issued the sign-in is not complete: the person is signed out on this browser and told that sign-in is unavailable.
- **A registration retried after its answer was lost.** If the Account was created but this session never got its grant, the form's retry (same command, same code) is let through the proxy for that one case (a POST to `/register` from a session that has an Account and no grant). The action replays the registration command and the database must confirm (`api.confirm_registration`) that this command and this code created the Account, before the session gets its grant. Any other session of a user that has an Account, with any other command or code, is sent to "Your session ended".
- **Valid** only while the Auth session it belongs to still exists for that user (a primary-key lookup in `auth.sessions`: a grant whose Auth session is gone is refused at once, not when it expires), it is not revoked, was issued less than **30 days** ago, was last used less than **7 days** ago, and its epoch is at least the Account's `authorization_epoch`. Its last use is written at most once a minute and never waits for another request's write. Auth's own time-box and inactivity timeout in `supabase/config.toml` stay in force as well, so whichever is shorter ends the session.
- **Revoked** (`api.revoke_grants`; the reasons so far are `sign_out`, `sign_out_others`, `step_up`, `subject_mismatch`, `disabled` and, from Story 1.6, `recovery`) by exactly one selector: a session, an Account (optionally sparing one session), or the Account's grants below an epoch. Revocation is final and audited (`session.revoked`, one event per grant). `api.raise_authorization_epoch` raises an Account's epoch, which makes every older grant stale at once without touching a row; the epoch only rises. **Any change of an Account's status raises the epoch by one in the same update** (a trigger, `identity.guard_account`, audited as `account.epoch_raised` by `system:accounts`), whoever makes it: a disabled Account's old sessions are stale for good, and enabling it again cannot bring them back. Revoking by Account or below an epoch takes the Account row `FOR UPDATE` (issuing holds it `FOR SHARE`), so a grant being issued at that moment is either seen and revoked or issued afterwards by a new sign-in, never missed. The revocation says how many grants it ended and how many of those were still in use; "sign out my other sessions" reports the second number. Story 1.5 (disable) uses the Account selector inside `api.disable_account`, with the reason `disabled`; Story 1.6 (recovery) uses `api.raise_authorization_epoch` and the Account selector inside `api.redeem_recovery`, with the reason `recovery`, before it grants the new session; Story 1.4a uses the session and Account selectors.
- **The pinned Google subject is checked on every authorization**: the Auth user must have exactly one Google identity, and it must be the subject pinned to the Account. Another Google identity linked to the same Auth user, or a replaced subject, revokes this session's grant, audits it once (`session.subject_mismatch`; only the request that actually revoked the grant writes it) and refuses the request, and every later request on that session is refused the same way (the grant keeps its reason), so each one signs the identity out. See the runbook below.
- **Sign out** (Account menu) revokes the session's grant first and only then asks Auth to end the session and expires the cookies, and lands on the sign-in page saying so. If the revocation cannot be recorded, the person is told (in the menu and through the page's live region) and stays signed in to try again; nothing is ended, and the message is gone when the menu is reopened. After a sign-out the old token is refused by Auth and, on its own, by the grant. A second press while one is running is ignored.
- **Sign out my other sessions** (Settings) revokes every other grant of the Account in one statement and then asks Auth to end the other sessions too (best effort, on a deadline: the revoked grants are what end them). The current session continues. It says how many sessions were signed out ("No other sessions were signed in" for none, in English and Hebrew); only grants that were still in use count. If the revocation cannot be recorded, nothing changes and the person is told. Both buttons read a Server Action answer that is not an action's (a proxy redirect, because the session has no access any more) as a reason to load the page once, which sends the person to the right sign-in message; any other failure is shown as unavailable and never reloads the page silently.
- **A session with no grant is refused as signed out.** That is also how existing sessions end at the cutover (below): there is no grandfathering, and nothing a private request does creates a grant.
- **Audit events** (append-only `identity.audit_events`, no content, no token, no address): `session.issued`, `session.revoked`, `session.subject_mismatch`, `account.epoch_raised`; and, from Story 1.5, `account.disabled`, `account.enabled` and the refusals `account.disable_refused`, `account.enable_refused` and `account.denied` (below); and, from Story 1.6, `recovery.issued`, `recovery.limited`, `recovery.rejected.<reason>`, `recovery.mail_failed` and `recovery.redeemed` (Administrator recovery, below).
- **The hosted preflight** (`check-env --live`, and the Vercel build) calls `api.preflight`, which reads one row at most of `identity.session_grants` (with the CSRF columns of Story 1.4c), `identity.accounts`, the step-up tables, `auth.sessions`, `auth.identities` and `auth.mfa_amr_claims` and writes nothing, so an unapplied migration, an unexposed schema or a missing privilege on a hosted `auth` table fails the build with one line instead of failing every private request after the deploy. Since Story 1.5 it also checks, from the catalog and without running them, that the six functions of the Accounts page and the authority contract exist (`N3020` names what is missing), that the service role may execute the five it calls (`42501`), and that the database owner may **delete from `auth.sessions`** (`42501`, "permission denied to end Auth sessions"): disabling ends the person's Auth sessions in the same transaction, so an environment that refuses that must fail the build rather than half-disable. Since Story 1.6 it also reads `identity.recovery_tokens` and the marker's `source` column, and checks from the catalog that the six functions of recovery exist (`N3020`, "the Story 1.6 migration is not applied") and that the service role may execute the four it calls (`42501`).
- **Rows accumulate**: one per sign-in, revoked or not; a periodic cleanup is planned with the scheduled jobs of Story 1.9 (see `deferred-work.md`).

## Step-up: fresh authentication for sensitive actions (Story 1.4b)

Administration, an owner's deletion of a Project or Export, Account deletion and closing the instance (later stories) must be preceded by proof that the person has just signed in again. Google offers no documented forced re-authentication and Supabase does not surface `auth_time`, so the proof is server-controlled: a deliberate **new Google sign-in, by the same person, that produces a new session**. It proves a deliberate new sign-in, not that Google re-checked a credential. Story 1.4b built the mechanism, the page that starts it and the checks a later story calls; the first area to use it is the Administrator's invitation page (Story 1.11, below), which is `administration`. No other class has a sensitive area yet.

**The four action classes** are `administration`, `owner_deletion`, `account_deletion` and `close_instance` (a closed list in `lib/step-up.ts`, repeated as check constraints in the database). The class decides where the person returns to after the step-up; the SERVER derives that path from the class in one table (`stepUpReturnPaths`: `administration` returns to `/admin`, the Administration index, because one class serves both of the Administrator's pages and the return path comes from the class alone; the other three return to Settings until the stories that own those areas exist) and never reads it from a URL, a form or a cookie.

**The flow.**

1. A sensitive area sends the person to `/step-up?for=<class>` (the invitation page does, for `administration`). The page is private (an active Account with a valid grant) and answers 404 for a class that is not on the list, and, for `administration`, for an Account that is not the Administrator (the page it returns to answers 404 to them, so the step-up toward it does too). The form has no field at all: the class is bound to the Server Action when the page renders (`beginStepUp.bind(null, class)`, the way Next.js passes extra arguments to an action) and the action checks it against the closed list again, so nothing the person types or submits is an Account, a session, a return path or a time. The class itself is the one thing a person can influence, by editing `?for=` or calling the action by hand; the worst that gets them is a marker of another class for their own newly signed-in session, which is nothing a step-up did not already give them. It has no navigation shell (one question: sign in with Google again) and a "Not now" link to the class's own return path (`stepUpReturnPaths`), not to wherever the person came from. It says what is being confirmed (one sentence for each class, `stepUpReasonKeys`) and which Google address is signed in (the verified address from Auth, never from the URL). Later stories send people here with `stepUpUrl(class)` (`lib/step-up.ts`), which builds the URL from the closed class list, instead of spelling the query string.
2. The Server Action (`app/step-up/actions.ts`) takes the Account and the session from the verified session (`withActiveAccount`), builds a Google sign-in **on the server** with `prompt=select_account` and no `login_hint` (a hint would suppress the account chooser) and `redirectTo` exactly `<origin>/auth/callback` (a query string fails Auth's allow-list), which writes its PKCE verifier into this browser's cookies, then calls `api.start_step_up`. The origin for `redirectTo` is the request's own (`x-forwarded-host` and `x-forwarded-proto`, else `Host`); a missing forwarded protocol is read as http only for a loopback host (127.0.0.1, localhost, [::1]) and fails closed for any other, because the cookie's `Secure` flag depends on it.
3. `api.start_step_up` writes one row to `identity.step_up_nonces`: the Account, the initiating session, the class, the SHA-256 of a random 256-bit secret, the PKCE challenge of that very sign-in (base64url SHA-256 of its verifier), a hash of the verified email, and a 10-minute expiry. **One nonce is open per Account** (a new start voids the old one), and **starts are limited to 10 an hour per Account**, counted from the nonce rows (the eleventh is `limited`, audited once an hour, and changes nothing). It refuses a session without a valid grant, a disabled Account and a Google identity that is not the pinned one (every comparison is `is distinct from`, so a NULL refuses and never falls through), and it dates the start from the moment it holds the Account's lock, not from the moment it was called. The email is compared as hashes of the lower-cased address, so an address that differs only in case is the same person. Only when the nonce exists does the action set the secret in an **httpOnly, SameSite=Lax cookie** (`nova3d-step-up`, `Secure` over https, 10 minutes) and send the browser to Google. The secret and the verifier are never stored or logged in readable form. **If the nonce cannot be written** (`limited`, `refused`, or the database does not answer) the Google sign-in the action had already started has left a PKCE verifier in the browser: the action undoes exactly that. The verifier cookies that start wrote (the fixed `-code-verifier`, the `-flows-code-verifier` index and the `-flow-<id>-code-verifier` slot) are removed, and a verifier of another sign-in that the start overwrote or evicted is put back as it was; the session cookie is never touched. An answer of `refused` means the session no longer has access (its grant ended, the Account was disabled, the Google identity changed), so it is logged (no secret in it) and the person is sent Home, where the access gate decides where they belong, instead of being told to try again.
4. Google's chooser is shown. The person signs in; Auth creates a **new session** and sends the browser to the ordinary `/auth/callback`.
5. The callback reads the step-up cookie and the PKCE verifier cookie BEFORE the code exchange (the exchange removes the verifier), exchanges the code, asks Auth who signed in, and, if the browser held a step-up cookie, hands the **new** session to `api.complete_step_up` with only the hash of the cookie secret and the challenge of the verifier it found. `complete_step_up` reads everything else from the database and from Auth's own tables, never from the caller, and:
   - **not a step-up** (`not_step_up`): the secret names no nonce, or the verifier is not the one this nonce's flow began (an ordinary sign-in started in another tab, or any sign-in started any other way). The callback carries on as for any sign-in. The step-up cookie is cleared on every path that reads it, in this case too: this browser holds one verifier (the most recently started sign-in's), another sign-in has overwritten and consumed the step-up's, so this step-up cannot come back here. It is also cleared when the exchange yields no user.
   - **accepted**, only if the nonce is open and under 10 minutes old, the Account is active and is this Auth user's, the session is not the initiating one and exists for this user, **Auth's own `auth.mfa_amr_claims` holds an `oauth` row for it created at or after the nonce start** (an `amr` claim in a token is never trusted), the user's one verified Google identity has the same email as at the start and the pinned subject, and the session can be given a grant the normal way. In ONE transaction it issues the new session's grant, writes the marker (this session, the class, 5 minutes), revokes the initiating session's grant (reason `step_up`), consumes the nonce and audits. The person lands on the class's return path.
   - **rejected** (another Google account, an expired or replaced nonce, a sign-in older than the nonce, anything else): the nonce is ended so it cannot be tried again, `step_up.rejected.<reason>` is audited against the Account, the new session gets no grant and no marker, **only that new session is ended, with local scope; no one is ever signed out globally**, and the person is sent to sign-in with the localized `step_up_failed` message. The exchange has already replaced this browser's session cookie, so they sign in again; the initiating session is untouched (its grant is revoked only on acceptance, so another browser that holds it keeps working).
6. If the database cannot be reached at step 5, nothing was accepted: the person is sent to sign-in with `auth_unavailable` (this browser's new session ended locally, nothing fresh). If it cannot be reached at step 2 or 3, the page says so and nothing is set or redirected.

**The marker** (`identity.fresh_authentications`) belongs to the new session and one class, and lives only in Postgres: never in a JWT claim, a token or Redis. `api.use_marker(user, session, class, started_after)` (typed as `checkMarker` in `lib/accounts.ts`) is what a later story's command calls, in the transaction of the sensitive change: the session must hold a valid grant of an active Account, and the marker must be this session's own, for this class, unexpired and unused. `administration` and `owner_deletion` markers are reusable for 5 minutes. `account_deletion` and `close_instance` markers are **consumed by use** (once, atomically) and need `started_after`, the moment the destructive confirmation was shown: a marker earned by a step-up that started at or before that moment is `stale` and is not consumed. Answers: `allowed`, `none`, `expired`, `used`, `stale`, `denied`. Since Story 1.6 a marker also has a `source`: `step_up` (it names its nonce) or `recovery` (written by Administrator recovery, which has no nonce, for the `administration` class and one session; see Administrator recovery below).

**Audit events** (append-only, opaque targets, no address, secret or hash): `step_up.started`, `step_up.completed`, `step_up.rejected.<reason>` (actor `system:step_up`, target `account:<id>`, one action per reason: `expired`, `replaced`, `used`, `disabled`, `mismatch`, `same_session`, `no_session`, `old_sign_in`, `grant_<outcome>`; the new session's own ID would not outlive its Auth session), `step_up.limited`, `step_up.marker_consumed`, plus the `session.issued` and `session.revoked` events of the grants it moves. `api.preflight` reads both new tables and `auth.mfa_amr_claims`.

**Why a stolen session cannot make itself fresh.** Whoever holds a stolen session can start a step-up, but only a Google sign-in of the same person (the same verified email, the pinned subject, a new session that Auth's own table shows came from a Google sign-in after the start) is accepted. Completed in another browser, it has no cookie and no PKCE verifier there (the verifier is in the initiating browser), so it is an ordinary sign-in or fails the exchange; with a different Google account it is rejected and only that new session is ended. A marker only ever belongs to a newly minted session, and acceptance revokes the initiating session's grant.

**Known limits.** The verifier binding reads the fixed `-code-verifier` cookie, which holds the verifier of the most recently started sign-in in that browser (the redirect URL carries no flow ID, because a query string fails Auth's allow-list). Starting another Google sign-in in the same browser between the start and the return of a step-up therefore makes the step-up's exchange fail (an ordinary `auth_failed`): it fails safe, and the person starts again. A route handler's `request.url` is not always the address the browser used (behind `next start --hostname 127.0.0.1` it names `localhost`), so the callback answers with relative `Location` headers, which the browser resolves against the address it used and which keep the session cookie with the sign-in. Anyone can start a step-up from any session of an Account, which voids the Account's open one and spends one of its 10 starts an hour (per Account, as the spec says); a per-session allowance and an alert on `step_up.limited` are recorded in `deferred-work.md`.

### Verifying the step-up on hosted Auth (Josh, AC-9)

The local tests run the real flow against a fake Google (below). Hosted Auth may differ, in particular a **single-session-per-user** setting would end the old session when the new one is created. Before relying on step-up on staging, with the migration `20261011120000_step_up.sql` applied (before the build that uses it deploys: the build's preflight reads the new tables and fails with one line if it is missing) and a throwaway Account, check each of these in order:

1. Sign in as the Administrator, open Settings, then Open Administration, then Open invitation codes, and press "Confirm it is you" (or open `/step-up?for=administration` directly). The page says what is being confirmed and which Google address you are signed in as. Press Continue. **Google's account chooser appears** (not a silent pass-through), on phone and desktop. (Administration returns to the Administration index, which answers 404 to anyone but the Administrator; to check the mechanism with a throwaway member, use `/step-up?for=owner_deletion`, which returns to Settings.)
2. Choose the same account. You land on `/admin` (the Administration index), signed in, and the page says you have confirmed it is you. Open Invitation codes: it says so too.
3. In the SQL editor, a **new `session_id`** exists, and its **`amr` row is at or after the nonce start**:

   ```sql
   select n.status, n.started_at, n.session_id as initiating_session, n.completed_session_id
     from identity.step_up_nonces n join identity.accounts a on a.id = n.account_id
    where a.user_id = '<user id>' order by n.started_at desc limit 1;

   select c.session_id, c.authentication_method, c.created_at
     from auth.mfa_amr_claims c where c.session_id = '<completed_session_id>';
   ```

   `status` is `completed`, `completed_session_id` differs from `initiating_session`, and `created_at` is not before `started_at`.
4. The **marker** exists for the new session only, with the class and a 5-minute life:

   ```sql
   select session_id, action_class, issued_at, expires_at, consumed_at
     from identity.fresh_authentications m join identity.accounts a on a.id = m.account_id
    where a.user_id = '<user id>' order by issued_at desc;
   ```
5. The **old grant is revoked** (`revoked_reason = 'step_up'`): `select session_id, revoked_at, revoked_reason from identity.session_grants where session_id = '<initiating_session>';` and the old session's browser is signed out on its next request.
6. **The single-session-per-user setting is off** (in the Auth settings for sessions; it is a paid-plan feature, so check that it is not on). If it were on, the new sign-in would end the initiating session at Auth, which is harmless for the flow (the marker is for the new session) but would sign the person's other devices out on every step-up; turn it off, or record it as a known behavior.
7. Repeat with **another Google account** chosen: you land on sign-in with "That sign-in could not be used to confirm it is you", no marker is written, the other account's new Auth session is gone, and the initiating session still works from another browser.
8. If the first step-up on staging fails with the sign-in message or "Sign-in is not available right now", look in the deployment logs for `A step-up sign-in was rejected` (it names a reason: `mismatch`, `expired`, `replaced`, `old_sign_in`, ...) or `The step-up could not be started` (names and messages only; no token, cookie or secret is logged).

Nothing in the repository applies any of this to a hosted project.

## Request integrity: origin and CSRF checks (Story 1.4c)

A valid session cookie is not enough for a request that changes something: the request must also come from this application. Two checks do that, and neither depends on the other being there.

**1. Origin: the proxy, for every request that is not safe.** GET, HEAD and OPTIONS are not checked. Every other method must carry an `Origin` that is present, is not the literal `null` (a sandboxed frame, a redirect across origins) and whose **host equals the first `x-forwarded-host`, else `host`**, which is how Next compares for Server Actions; and a `Sec-Fetch-Site` that is not `cross-site`. Next itself checks Server Actions only, and lets a request with no `Origin` through; this check is stricter, and it covers route handlers too. It runs **after** the access decision (`proxy.ts`), so a request that is denied keeps its own answer (401, 403, or the redirect to sign-in) and only a request that would otherwise proceed is refused, with a **403: JSON `{"error": "origin_not_allowed"}` for `/api`, a plain `Forbidden` elsewhere, never a redirect**. It also applies to public paths (a POST to `/api/health` or `/login` from another site is a 403 too). Both the decision and the headers it reads are in `lib/request-integrity.ts` (pure, tested without a server); there is no CORS header anywhere and no setting to allow another origin (`serverActions.allowedOrigins` is not set and should not be).

- **Hosts are compared as a browser spells them: lower-case, with the default port of the Origin's own scheme dropped.** `Host: app.example:443` is the host of `Origin: https://app.example`, and `:80` of `http://`; a different port (`:8443`) is a different host.
- **The scheme is not compared.** Next does not compare it for Server Actions either, and a host alone cannot tell a page served over http from one served over https. What stops a request from a downgraded page is HSTS and the Secure cookies, not this check; revisit it if a hosted environment ever serves http.
- **Each refusal is logged as ONE line that names the rule and the method and nothing else** (`A request was refused for its origin. origin_mismatch POST`): never a header value, a path or a query, because every one of them is the sender's. The rules are `origin_missing`, `origin_null`, `origin_invalid`, `origin_mismatch`, `cross_site` and `host_missing`. Nothing counts or alerts on them yet (`deferred-work.md`, Story 1.13).
- **`Referrer-Policy: no-referrer` must never be set.** A form that a browser posts with that policy carries `Origin: null` (the Fetch standard serialises the origin that way for a non-GET request that is not a CORS request), which is refused here, and a Server Action posted natively with JavaScript off would stop working. The application sets no `Referrer-Policy` and no `<meta name="referrer">`; `tests/e2e/request-integrity.spec.ts` checks both, and shows what a page that did set it would break.

**2. A per-session CSRF token: route handlers that are not Server Actions.** Every non-GET route handler under `app/api` starts from `requireMutationAccess(request)` (`lib/auth.ts`), which, in this order: repeats the origin check (the proxy alone is not a boundary), runs `requireApiAccess` (the active Account and a valid grant), and compares the SHA-256 of the request's `x-csrf-token` header with the hash stored on the grant of the **verified** session (`api.verify_csrf`; the user and the session come from the verified token, never from the request). Its denials are 403 `origin_not_allowed`, 403 `csrf_invalid` (no token, a malformed one, a wrong one, another session's), 401 `session_ended` (the grant ended between the two checks), a **retryable 503** when the database cannot answer (an `AccountsUnavailableError`) and a **non-retryable 500** `internal_error` for anything else that throws, which is a bug and is logged as one; in every case nothing has changed. `tests/unit/gate-structure.test.ts` reads every `route.*` under `app` (not only `app/api`) and fails if a POST, PUT, PATCH or DELETE handler does not start from `requireMutationAccess(<its own first parameter>)`, or if a route exports a handler in a way it cannot classify. The one line it lets stand ahead of the guard is the synthetic route's 404 (below). A **Server Action needs no token**: Next's host check and the proxy's origin check cover it, and nothing in an action reads one.

**The token.** 256 random bits (43 URL-safe characters) per session. Only its SHA-256, under the domain label `nova3d/csrf-token/v1`, is stored: `csrf_hash` and `csrf_issued_at` on `identity.session_grants` (migration `20261011130000_request_integrity.sql`), so a copy of the database cannot forge one, and a token is worth nothing once its grant is revoked, expired, idle or stale (`api.verify_csrf` asks `api.authorize_session` first). It is delivered in the cookie **`nova3d-csrf`**, which page script reads and echoes in the header **`x-csrf-token`** (`lib/csrf-client.ts`: `readCsrfToken`, `withCsrfToken`, `csrfFetch`; browser-safe, no server import). The cookie is **not httpOnly** (script must read it), **SameSite Lax**, **path `/`**, **Secure when the browser reached the application over https** (the first `x-forwarded-proto`, else the request's own protocol), and a **session cookie** (no expiry of its own). A page that sets it is always sent `Cache-Control: private, no-store`, whatever a refreshed session had set, so a shared cache never stores, and hands to someone else, a response that carries one person's token.

**The browser helper sends to this application only.** The token is readable by script on purpose, so `csrfFetch` resolves its target against the page's address and, if the origin is not the page's, rejects with a `TypeError` and sends nothing. Given a `Request` it keeps that request's headers (`init.headers` win over them), and `readCsrfToken` reads every cookie of the name and returns the first that is shaped like a token, so a stale or planted cookie of the same name does not hide the real one.

**How a session gets its token.** The proxy issues it on an **authorized page request** (a browser navigation to a document: a GET with `Sec-Fetch-Dest: document`, or, from a browser that sends no fetch metadata, an `Accept` that asks for `text/html`; not a client-side navigation, a prefetch, a speculative load (`Sec-Purpose: prefetch` or `prerender`, the older `Purpose: prefetch`) or an `/api` call) from an active Account that **carries no usable `nova3d-csrf` cookie**: one that is missing, empty, or not shaped like a token (a truncated or planted value would otherwise keep the real one from ever being issued). `api.issue_csrf` stores the hash when the grant has none or its hash is **60 seconds old or older**, and otherwise leaves it; only a hash that was stored is delivered. So two tabs that make their first request at the same moment keep **one** token (the second finds a fresh hash and sets nothing, so the cookie and the stored hash never differ), a cookie lost for good is replaced on the next page request once the hash is a minute old, and an attacker can neither read the new cookie nor make the token change while the victim's cookie exists. If the database cannot answer the page renders without a cookie (nothing is blocked, the failure is logged by name) and the next page request tries again. Grants made before this story, and the new session a step-up creates, get theirs on their next page request, with no sign-out and no change to how grants are issued, revoked or stepped up.

**The cookie goes with its session.** Because the proxy issues a token only to a browser that has no usable cookie, a cookie left over from an earlier session would keep the next session from ever getting its own (every mutation would then be `csrf_invalid` until the browser dropped it). So the sign-in callback removes the cookie as soon as the code exchange has given the browser a different session (a new sign-in, or the new session a step-up mints), and the sign-out action removes it with the session. A cookie that cannot be removed never fails a sign-in or a sign-out; the failure is logged by the error's name only. A session ended some other way (a disabled Account signed out by the proxy, a grant that expired) is followed by a sign-in, which goes through the callback.

**The synthetic route.** `app/api/kit/mutation/route.ts` is a counter per Account in the server's memory: a GET reports it and a POST bumps it. It exists so the tests have a real route mutation, which is not a Server Action, with state they can see; it has no other behavior. It checks `SYNTHETIC_DATA_ENABLED` **first** and answers 404 unless it is exactly `true` (the flag that opens `/kit`), before any access, token or database call, so a deployment that has no such route spends nothing on one. Production cannot enable synthetic data (`check-env`); **staging and local run with it on, so on those the route is live.** With it on, the route is private: a signed-out request is a 401 like any other `/api` path.

**What a proxy in front of the application must forward.** The origin check compares what the browser put in `Origin` with the host the application is reached at, so a platform, CDN or reverse proxy in front of it must forward `Origin`, `Sec-Fetch-Site` and `Cookie` untouched, and must present the public host either as `Host` or as the first `x-forwarded-host` (and `x-forwarded-proto` for the cookie's `Secure` flag). One that rewrites `Host` to an internal name without setting `x-forwarded-host`, or strips `Origin` from a POST, makes every mutation a 403 (a Server Action included, which is why it is the first thing the hosted check below looks at). Vercel sets `x-forwarded-host` and `x-forwarded-proto` and forwards the rest.

**Things to know.**

- **Next (16.3.5, as observed) runs the proxy twice for a request that carries the `RSC` header, and removes `RSC` and `Next-Router-Prefetch` before the proxy sees them.** So the proxy tells a client-side navigation or a prefetch by its `Sec-Fetch-Dest: empty`, never by those headers, and a token cookie is set only on a document navigation, which runs the proxy once. A request that ran it twice would lose the cookie of the first run: the second run would find the hash the first had just stored, say `exists`, and set nothing. `tests/e2e/request-integrity.spec.ts` clicks a real `<Link>` and checks that no token is issued.
- **A cookie lost in the middle of a visit comes back only on a full page load.** A client-side navigation never issues a token, so a script that mutates with no cookie is refused with `csrf_invalid` until the person loads a page. No screen mutates through a route yet, so nothing handles that case in the browser (see `deferred-work.md`).
- **A route mutation costs three authorizations** (the proxy's, `requireApiAccess`'s and `api.verify_csrf`'s, which asks `api.authorize_session` itself); see `deferred-work.md`.
- **The comparison is of two SHA-256 digests in SQL**, which is not constant-time and does not need to be: an attacker cannot choose a token to steer a digest.
- **A refused request leaves no row**: nothing is written to the database or the audit trail for a bad origin or a bad token (the proxy and the route would make an attacker's noise into rows). The origin refusals are logged by rule and method (above); the token refusals are not logged at all.

## Account preferences and the isolation proof (Story 1.4d)

**The record.** Language, light or dark, explanation detail and the first-use introduction belong to the Account, not to a device: `identity.account_preferences` (migration `20261011140000_account_preferences.sql`), one row per Account (`account_id` is the primary key and references the Account with `ON DELETE RESTRICT`). `locale` is null while the Account follows its device's language, otherwise `en` or `he`; `theme` is `light` or `dark`; `detail` is `simple` or `technical`; `guidance` is `shown` or `dismissed`. The CHECK constraints are the allowed values of `lib/preferences.ts`, and `tests/integration/account-preferences.test.ts` reads them back from the database and fails if the two drift apart. The table follows the pattern of every other Identity table: row-level security on, no policy, no privilege for `anon`, `authenticated` or `service_role`; the only callable surface is two `api` functions, executable by the service role alone, that take the **Account ID the server derived from the verified session, never a client's**: `api.adopt_preferences` (inserts only when the Account has no record: `created`, `exists` or `denied`) and `api.set_preference` (validates one name and one value and saves it: `saved` or `denied`). Both refuse an Account that is not active (`denied`), and both treat a name or value outside the allowed sets as an invalid argument (`22023`), never as something to fix up. Nothing about preferences is audited: they are not sensitive, and a record of every theme change would only grow the append-only table.

**It rides on the live authorization.** `api.authorize_session` now returns the Account's record (or null) in its **active** answer, through one more primary-key read and **no extra round trip**, so the record cannot disagree with the Account being authorized and no state but `active` ever carries one. `lib/access.ts` hands it to the page as `account.preferences`; a record that is not a record (a value outside the sets, a field missing) reads as none, so preferences can never change an access decision.

**The record wins, and the cookies stay a copy.** For an active Account that has a record, the root layout, the page metadata and `getI18n` render from it (`lib/preferences.server.ts`), whatever the cookies of this device say: that is how a **new device** shows the Account's choices, and how a change made on **another device** shows on the next page load (nothing polls, pushes or syncs live; a long-open tab learns of it when it next loads a page, not on a client-side navigation, because Next keeps the root layout between those; until then the page's own title may already follow the new language while the page does not, see `deferred-work.md`). The layout asks for the Account only when the request carries an Auth session cookie, so the sign-in page and the design kit cost nothing signed out; the memoized `getAccess` makes it free for a private page. The four device cookies (`nova3d-locale`, `-theme`, `-detail`, `-guidance`) still serve pages with **no Account** (the sign-in page, the kit), an Account with no record yet, and any request whose Account could not be read (an outage, a session that is not active). They are also the copy a change writes, so the sign-in page follows the person after they sign out. Which of these pages save to the Account is decided per request (`accountBacked`): an active Account does, and so does an Account that **could not be read** (an outage: it may well have a record, so a change goes through the Server Action and fails visibly with the notice, instead of being written to the cookie alone and silently overridden by the record later); a signed-out visitor, a session that ended, an identity with no Account, a disabled Account and a changed Google identity stay cookie-only.

**A first sign-in adopts the device.** On an authorized **page navigation** (a document request; not a client-side navigation, a prefetch or an `/api` call) of an active Account whose answer carries no record, the proxy (`adoptDeviceChoices`, `proxy.ts`) hands the Account's four valid cookies to `api.adopt_preferences`. An absent or tampered cookie is the default (light, simple, shown) and a language no valid cookie chose is `null`, so a device with no cookies adopts "follow my device". It covers every way a first session starts that ends in a **full page load** (the sign-in callback's redirect, the `/register` claim); the registration form's landing is a Server Action redirect, which is a client-side navigation, so it adopts at the next full page load. Two first requests at once leave **one** record (the second gets `exists`); and **a failure is logged (the error's name and message only) and never blocks the page**, which renders from the cookies, and the next navigation tries again. After that the record is the Account's and the device's cookies are ignored. A shared device means a new Account's first sign-in adopts whatever the last person left in the cookies; they are not sensitive and the person can change them.

**A change made signed in** goes through a Server Action behind `withActiveAccount` (`app/account/preference-actions.ts`, `savePreference(name, value)`): it takes a name and a value and nothing else, checks both against the allowed sets, saves the record (adopting the device's cookies first if the Account somehow has none, so changing one setting does not drop the other three) and **only then** writes the cookie copy (a null language removes it). The client (`components/preferences-provider.tsx`) applies the change at once, saves in the background, one after another in the order the choices were made (`createPreferenceSaveQueue`, `lib/preference-actions.ts`: a save that throws a redirect, or never answers within 12 seconds, a few seconds above the server's own 8-second budget, cannot stop the saves behind it), and **undoes it, with the reason in the page's live region (once for each failure) and in words** (`components/ui/preference-notice.tsx`, a region of its own, shown on the sign-in, registration and step-up screens too), if the record could not hold it; on success it asks the server for the page again, once the last save is done. Dismissing the words moves focus to the page content. A browser that refuses cookies still has the choice saved: the record wins. A session that no longer has access (signed out elsewhere, disabled) is not told "could not save": the page loads again and sends the person to sign in, like the sign-out buttons. Anywhere no Account is signed in, a choice stays cookie-only as before.

**The sign-in page** offers English or Hebrew and light or dark (`components/login-preferences.tsx`): two radio groups, so the page still has the one button, announced like the same choices in Settings. For a visitor with no session (the usual one) the choice is **cookies only**: adopted at the first sign-in, ignored once the Account has a record. A visitor who **holds an active session and opens `/login`** (a public path) is rendered for their Account like any other page, so their choice there is saved to the Account, undone and said so if it cannot be, exactly as in Settings; the notice is shown on this page too.

**The isolation proof** (AC-1) is `tests/integration/isolation.test.ts`. It registers two real Accounts, each with a session and grant, a CSRF token, a preferences record and a private object in a private storage bucket, and has one try the other through: the REST API (every `api` function, with the other Account's IDs, for the other Account's token, an anon token and the anon key; every table of `identity` and `projects`, which is not exposed; `lifecycle.instance_identity`, which is exposed and closed), direct database roles (anon, authenticated with either Account's claims, and the service role, which has no table access either), the `api` functions called with the other Account's IDs (a session that is not the user's is `no_session` or `denied` and changes nothing), the Storage API and the storage tables (Supabase ships **no policy** on `storage.objects` or `storage.buckets`, so a browser role is denied by default, and the test pins that), and composite ownership foreign keys on scratch tables in a transaction that is rolled back (a child cannot name a parent of another Workspace, at insert or update; a single-column reference, shown as the control, can). The last part is the forward guard: it lists **every relation, function and schema in `identity`, `projects` and `lifecycle` from the catalog**, never from a list in the test, and fails for anything `anon` or `authenticated` (or PUBLIC) can reach, so a table added by a later story is checked without anyone adding it; the test shows the guard failing for each kind of opening, in each schema, and for a table in `api`. A later story's table is made the way the guard expects: row-level security on, no policy, no grant to a browser role.

The build's preflight (`api.preflight`) now also reads the new table and fails with one line if it is missing; the previous build keeps working with the migration (the extra field in the authorization answer is ignored). No session ends, no setting or secret is involved, and **rolling back** is a redeploy of the previous build with the migration left in place. The first real sign-in after the deploy adopts the cookies of that browser; the checks are in `docs/staging.md`, step 5. The Hebrew of the new strings (`settings.lede`, `settings.announce.saveFailed`, `notice.dismiss`, `login.prefs.title`) is machine-drafted, like the rest, and needs the same native review (`deferred-work.md`).

## Invitation management: the Administrator's page (Story 1.11)

`/admin/invitations` (AD-01) is where the Administrator issues and revokes invitation codes without the command line. It is the first area that needs the step-up (`administration`).

**Who sees it.** Only an active Administrator. Any other Account gets the same 404 page as for a page that does not exist (`requireAdministrator` in `lib/auth.ts`: it starts from `requireActiveAccount`, so a signed-out visitor goes to sign-in as for any private page, and a member gets a 404, not a redirect). The role is the live authorization's, so it follows a change of role on the next request. Settings shows an Administration section with a link to the Administration index (`/admin`), to the Administrator only (the pages do not rely on that); Back from the invitation page goes to the index, and Back from the index goes to Settings (Story 1.5).

**What it does.** Three Server Actions in `app/admin/invitations/actions.ts`: issue a named code (a label, not bound to an address), make the general code or replace the unused one, and revoke an unused code. Each runs behind `withActiveAccount`, which asks for the live authorization itself, and in this order, with nothing changed before all pass:

1. **The role.** The Account's role is `administrator`. Otherwise nothing is changed and the attempt is audited as `invitation.denied`. The one thing read from the form before this check is a revoke's `invitationId`, because a refusal is audited against that invitation; it is parsed to a UUID or null at once and nothing else is looked at. The name of a named code and the general code's `replace` flag are read only after the role and the marker have passed.
2. **The marker.** `checkMarker` for `administration` on the verified session. `allowed` goes on; `none` or `expired` is a refusal that offers the step-up (a link to `/step-up?for=administration`); `used` or `stale` (which an `administration` marker never is) is a refusal without it; `denied` (the session lost its grant a moment ago) sends the person Home for the access gate to decide; a database that cannot answer is a retryable "nothing was made". A refusal is audited as `invitation.issue_refused` or `invitation.revoke_refused`. The marker is checked in the action and not inside `issueInvitation` because the audited seed command shares that function and has no session; an `administration` marker is reusable for its five minutes, so a check followed by the call loses nothing.
3. **The change.** `issueInvitation` or `revokeInvitation`, with the actor `user:<Auth user ID>` taken from the verified session and never from the request. They are the functions the seed command calls and they audit the change (`invitation.issued`, `invitation.revoked`; replacing the general code audits both).

**A code is shown once.** The value is returned in the one response of the action that made it and is held in the page's memory only (React state): not in a URL, a cookie, the browser's storage or the router's cache, and never logged, audited, listed again or stored (the database keeps its HMAC). The page shows it with a Copy action and a "Hide the code" button; a second code made before the first was hidden does not take its place; leaving the page loses it, which is what "once" means. If Copy is refused by the browser the code is selected and the page says so. The list shows each code's identifier, name, kind, status (Unused, Used, Revoked, each as a word and a shape) and creation time (written `2026-10-12 00:24 UTC`, the same on the server and in the browser), newest first, and nothing from which a code could be recovered.

**Confirmations.** Replacing an unused general code (which revokes the current one) and revoking any code ask first, in a dialog that starts on Cancel. A name is normalized first (each run of control characters, tabs, newlines and NUL included, becomes one space, and the ends are trimmed), must then show something (a name of nothing but zero-width, format, space or fill characters is empty) and be at most 80 characters, counted as the database counts them; a format character beside visible text, such as a right-to-left mark in a Hebrew name, is part of the name and is kept. The form says so in the field before sending anything, and the action checks again with the same functions (`lib/invitations.ts`).

**When something is not known.** If the marker cannot be checked, nothing was sent, and the page says so. If the issue or the revoke itself gets no answer, the change may have been made: the page says it does not know, re-reads the list so that "check the list below" points at a list read after the attempt (the codes already on screen stay), and tells the person to revoke any code they do not recognise. A refusal for want of a fresh sign-in also re-reads the page, so the "you have confirmed it is you" note gives way to the step-up note. Two windows making the general code at once: one makes it, the other is told one exists and its page catches up.

**Refusals are audited without content.** `api.record_invitation_refusal` (migration `20261012120000_invitation_refusals.sql`, service role only) records the actor and, for a revoke, the invitation as the target when it exists (an ID that names nothing is recorded with no target, so inventing IDs grows nothing), once an hour for the same actor, action and target (under an advisory lock, so also under concurrency). It takes no label, code, hash, marker outcome or reason text, and the audit table has no column that could hold one. It checks that the Account is real and that the refusal is the kind that Account can make (`invitation.denied` only for an Account that is not the Administrator; the other two only for the Administrator). A failure to record is logged by name and never turns a refusal into a permission.

**If the list cannot be read** the page still renders: it says the codes could not be loaded, makes no claim about whether a general code is waiting (it neither says "waiting" nor "none waiting"), and offers to make one, which is safe because without `replace` a server that already holds an unused general code answers "exists" and changes nothing. If the marker cannot be read when the page renders, the page shows neither the "confirmed" note nor the "needs a fresh sign-in" note, and the actions decide. The page's title is the 404 page's for anyone but an active Administrator, so a member's 404 names nothing about it.

**Known limits.** The list is the 200 newest codes (`api.list_invitations`), so an unused general code older than that would be shown as "none waiting" (the next attempt to make one is told one exists). The hash-key canary (`deferred-work.md`) is not built: a key that no longer matches makes outstanding codes unredeemable without a message here. A step-up that fails after Google ends on the sign-in page and does not bring the person back to this page with a message (`deferred-work.md`).

## Account administration: disabling and re-enabling (Story 1.5)

`/admin/accounts` (AD-02) is where the Administrator sees who has an Account and turns one off or on. `/admin` becomes the **Administration index** (links to Invitation codes and Accounts) and is where the `administration` step-up returns: the return path is derived from the class alone and one class serves both pages. It follows the invitation page's pattern exactly, and shares its wrapper (`lib/administered.ts`).

**Who sees it.** Only an active Administrator (`requireAdministrator`); anyone else gets the 404 page of a page that does not exist, with that page's title. The list shows, for each Account, the verified Google address (from Auth, via `identity.verified_google`), the name of the invitation that made it (or "General code", or "No code (set up directly)" for the pre-authorized Administrator), the role, the status in words and shapes (Enabled, Disabled) and the creation time, newest first, at most 200 (`api.list_accounts`). It never shows or reads a Workspace, a project name or usage: the database function does not select them, and a structural test pins that no page, action, component or list function names one.

**The two changes.** Two Server Actions in `app/admin/accounts/actions.ts` (`disableMemberAccount`, `enableMemberAccount`) go through `administered`, which runs, behind `withActiveAccount` and with nothing changed before all pass: the role is `administrator` (otherwise `account.denied` is audited against the Account named), then the `administration` marker (`checkMarker`; only `allowed` passes: no marker, an expired one, or a marker of another class comes back as `none` or `expired`, is audited as `account.disable_refused` or `account.enable_refused`, and offers the step-up), then the database function with the actor `user:<Auth user ID>` from the verified session, never from the form. The only thing read from the form before the role check is the Account's ID, parsed to a UUID or null. Both ask first in a dialog that starts on Cancel.

**Disabling is one database transaction** (`api.disable_account`), under a lock on the Account row (`FOR UPDATE`): the status changes (which raises the authorization epoch and audits `account.epoch_raised`, `identity.guard_account`), every session grant of the Account is revoked (`api.revoke_grants`, reason `disabled`, audited per grant), **its Auth sessions are deleted** (`delete from auth.sessions` by the function's owner, which `api.preflight` probes), and `account.disabled` is audited with the actor and the opaque target `account:<id>`. The Workspace, the registration, the invitation and the preferences are untouched. An Administrator's Account cannot be disabled (the function refuses it; the Administrator's way back in is Administrator recovery, below). Two windows disabling at once are one disable and one "already disabled". Re-enabling (`api.enable_account`) sets the Account active under a **newer epoch** and audits `account.enabled`; nothing is restored: the grants stay revoked, the Auth sessions stay ended, and the person signs in anew with Google.

**What the disabled person sees.** Their sessions no longer exist in Auth, so their next request is signed out at once with the ordinary "sign in" message and no private content; the **disabled message** is what they see when they sign in again (the callback finds the Account disabled and signs the new session out everywhere). A request that races the disable and reaches the authorization first is told it is disabled. After a re-enable, a new sign-in gets in under the newer epoch.

**The authority contract** (`docs/authority-contract.md`, `lib/authority.ts`): every Job and file path asks before each step that publishes or reaches outside. An operation registers under the epoch of the live authorization that started it (`operationOf(access.account)`). `authorizeStep` (the application's own steps; `api.guard_operation`: `allowed`, `disabled`, `stale_epoch`, `no_account`, and a check that cannot be made is **denied**) and `identity.assert_operation_authority(account, epoch)` (SQL that publishes: takes the Account row `FOR SHARE`, so a disable cannot commit between the check and the write; raises `N3010`). An operation registered before a disable stays denied after a re-enable, because both raised the epoch. **Cancellation signals go out only after the disable has committed**: cancellers registered by later stories (`registerCanceller`) run best effort, together, each with a time limit, and are counted; none exists yet, so the page says 0 Jobs were cancelled. A canceller that asks the guard always finds it denying.

**Refusals are audited without content** by `api.record_account_refusal` (service role only, in the pattern of `api.record_invitation_refusal`): `account.disable_refused` and `account.enable_refused` (an Administrator without a valid marker) and `account.denied` (an Account that is not the Administrator), with the actor and, when it exists, the Account as target; once an hour per actor, action and target, under an advisory lock; never a reason.

**When something is not known.** If the marker or the authorization cannot be checked, nothing was sent and the page says so (retryable). If the disable or enable itself gets no answer, it may have been made: the page says it does not know, re-reads the list, and tells the person to check it first. If the list cannot be read, the page still renders and says so.

**Known limits.** The list is the 200 newest Accounts. Cancellers are in-process (a registry on `globalThis`): the stories that add Jobs decide where they run and may need a queue-backed canceller (`deferred-work.md`). Disabling an Account whose person is mid-sign-in is safe either way (the grant is refused while disabled, and `api.issue_grant` waits for the lock).

## Administrator recovery (Story 1.6)

If the Administrator's Google sign-in is lost or failing, nothing lets them back in short of database access, and no non-Google path exists (the Email provider stays off). Recovery is the one way back in, and it serves exactly one person: the sole Administrator. A public Recover page mails a single-use link to the Administrator's own address, a confirmation page turns it into a session through Auth's Admin API, and one database transaction ends every earlier session of the Account and gives the new one a fresh `administration` marker. Nothing about it enables the Email provider or any other sign-in credential: the new session is minted for the Auth user's own Google-backed account (see "Known limits" for what is and is not verified on hosted Auth).

**What exists.**

- `/recover` and `/recover/confirm`: two public pages with no navigation shell (`lib/public-paths.ts`, `isChromeless`), in English and Hebrew, light and dark. The sign-in page has a quiet "Administrator recovery" link to the first. Both act through Server Actions (`app/recover/actions.ts`: `requestRecovery`, `redeemRecovery`), never a POST route, and a public path is not exempt from the proxy's origin check on a POST.
- The migration `20261012140000_administrator_recovery.sql`: the closed table `identity.recovery_tokens` and four functions, `api.issue_recovery`, `api.void_recovery`, `api.check_recovery` and `api.redeem_recovery`, all executable by the service role alone, plus the one edit to the step-up marker table (below) and a preflight that probes all of it.
- `lib/recovery.ts` (both sequences, with every collaborator injected so each order and failure is tested without a database), `lib/mailer.ts` (the one door the application mails through), `lib/auth-admin.ts` (the one place the Auth Admin API is called), `createDeferredSupabaseServerClient` in `lib/supabase/server.ts`, `lib/recovery-state.ts` (what the pages and the actions agree on), and the typed calls at the bottom of `lib/accounts.ts`.

**Who is eligible.** The one **active Account with role `administrator`** whose Auth user's verified Google address (`identity.verified_google`, read from Auth) equals `ADMINISTRATOR_EMAIL`, and whose **pinned Google subject is still the Auth user's one Google identity**. The server passes that address to the database from its own environment; no request supplies an address, a recipient, a link origin or an Account. None, or more than one, is refused and audited (`recovery.rejected.administrator`), and nothing is issued or mailed. **Recovery re-pins nothing**: re-pinning a changed Google subject stays a database operation (the runbook below, and `deferred-work.md`). Never: recovery for a member, a second Administrator, impersonation or Workspace access.

**Asking for a link** (`/recover`: one button, no input). `requestRecovery` issues a token and mails it:

1. The token is 32 random bytes, base64url (43 characters), made by the application. Only its HMAC-SHA-256 under `RECOVERY_HASH_KEY` is stored in `identity.recovery_tokens`, with its issue, expiry, use and void times. It lives **15 minutes on the database clock**, and **one is outstanding** at a time.
2. **Issuance is limited globally** (not per visitor): **1 per 15 minutes and 5 per 24 hours**, and every issuance counts, a voided one included. A request over a limit is `limited`, audited once an hour (`recovery.limited`), and issues and mails nothing.
3. The link is `<origin>/recover/confirm#<token>`, mailed **only to `ADMINISTRATOR_EMAIL`**, through `lib/mailer.ts`, where the recipient is not a parameter. **The token is in the URL fragment**, so no server, proxy, platform log, `Referer` or audit row ever sees it (a query string would reach Vercel's request logs, and `Referrer-Policy: no-referrer` is forbidden here, see request integrity above). `<origin>` is `APP_ORIGIN` in staging and production (required there, an https origin; no request can choose it) and, locally, the origin the request came in on. If there is no usable origin nothing is issued, so no issuance is spent for nothing.
4. The page answers only **sent**, **limited** or **unavailable**, and never an address, a name or a Workspace. No eligible Administrator, a mail failure, an outage and an unusable `APP_ORIGIN` all read "not available right now", so the page teaches nothing. Where the cause is kept differs: for no eligible Administrator the database audit holds it (`recovery.rejected.administrator`), and for a mail failure it is `recovery.mail_failed`. A database that does not answer and an unusable `APP_ORIGIN` leave no audit row (no token was issued, or there was nowhere to write one): the cause is in the deployment logs only, as a fixed message with an error's name and message and nothing else.
5. **A mail that fails.** A definitive refusal (Resend answered with a status below 500, or nothing here could be sent) **voids the token**, so nothing usable remains, and audits `recovery.mail_failed`. An unknown outcome (a timeout, a network failure, a 5xx, a redirect) **only audits** `recovery.mail_failed` and leaves the token valid: the mail may have arrived, and voiding it could lock the Administrator out for 15 minutes after a mail that did. Either way the issuance still counts toward the limits.

**The mail** (`lib/mailer.ts`): one message with the link and nothing else that is private. Staging and production send through Resend (`POST https://api.resend.com/emails`, `RESEND_API_KEY`) from `onboarding@resend.dev`; the `resend.dev` sender reaches only the address the Resend account is registered with, so **that account must be registered with the Administrator's address** (ledger item `resend-account`). It is a plain `fetch` (the dependency set is pinned, so no SDK) with a 10-second timeout and no redirects (`redirect: 'error'`, so the key can never follow one to another host); the response body is never read, and **nothing is logged**: not the link, the address, the key, a request or a response (a log line is a fixed reason word). With `APP_ENV=local` it sends to the Supabase stack's own Mailpit over HTTP (`http://127.0.0.1:54324`, `/api/v1/send`; the host is the one the loopback Supabase URL names), so the application and the tests share one real path; no test calls Resend, and the Resend transport is covered by unit tests with a faked `fetch` (`tests/unit/mailer.test.ts`) and by the staging check below.

**Opening the link** (`/recover/confirm`, public). A GET only renders, and the fragment never reaches the server, so **a mail scanner's GET (or a HEAD, or a token wrongly put in the query) changes nothing and cannot see the token**. The page's script reads the fragment in the browser, replaces the address without it (so it is not in the history or a copied address) and holds the token in memory in a hidden field of a form whose one button POSTs `redeemRecovery`. It shows the link being read, a link that cannot be used (no fragment, not a token, or one the server then refused: one message, which also says that a person who reloaded the page should open the link in their email again, because the fragment is taken out of the address on purpose and a reload has none, before it offers "Ask for a new link"), a notice in a browser with script turned off that confirming needs script (the button waits for the page to read the link), the form, and the two answers described below (try again, and unknown).

**The redemption**, in this order (`redeemRecoveryLink`):

1. **Check the token** (`api.check_recovery`): unused, unvoided, unexpired, and its Account still the one eligible Administrator. It is read-only apart from auditing a refusal. Nothing has been made yet, so a failure here leaves nothing behind.
2. **Ask Auth's Admin API for a link** (`lib/auth-admin.ts`: `POST /auth/v1/admin/generate_link`, type `magiclink`, with the Auth user's own address, which the check read from Auth). It must answer for the same Auth user.
3. **`verifyOtp`** turns that link into a session on a **cookie-bound client whose cookie writes are held back** until the outcome is known (`createDeferredSupabaseServerClient`). A browser with two windows shares one cookie jar, so a window that loses the race must not leave its own, doomed session cookie (or an expiry over the winner's cookie) in the response it gives back. Until the transaction below commits, only an inert, grant-less Auth session can exist, and it reaches no private path.
4. **One database transaction, `api.redeem_recovery`, under a lock on the Account** (`FOR UPDATE`, which two windows redeeming the same link queue on, so exactly one recovers): it re-checks the token and the eligibility and marks the token used; raises the authorization epoch; revokes every grant of the Account (`api.revoke_grants`, reason `recovery`, audited per grant); deletes every other Auth session of the person; issues the new session's grant (`api.issue_grant`, after the epoch is raised, so it carries the new one); writes the new session's **marker** (class `administration`, 5 minutes, that session only, source `recovery`, no nonce); and audits `recovery.redeemed`. **Any refusal undoes all of it** (the work runs in a sub-transaction, so even the audit events of a failed grant go), then audits `recovery.rejected.<reason>`. A new session that cannot hold a grant (the pinned subject no longer matches, the Account is disabled, Auth has no such session) is such a refusal (`N3030` inside the function, recorded as `recovery.rejected.administrator`).
5. **The browser.** The held cookies are written, the CSRF cookie (it belonged to the old session) is cleared, and the person goes to `/admin?recovered=<n>`, where `n` is the number of other sessions that were signed out. The number is for the words only and grants nothing: a changed one only shows a sentence to the person who typed it.

**When something goes wrong.**

- Before `verifyOtp`: nothing exists and nothing changed. The page says it could not finish and that the link still works until it expires; trying again is safe.
- After `verifyOtp`, a refusal or a failure that is certainly not a commit (the database understood and rejected the call): **only that new session is ended**, locally and never globally, and no cookie is written, so the browser keeps exactly the cookies it sent. The token is unused unless the transaction committed.
- A database that does not answer **after** the transaction was handed to it (a timeout, a 5xx) is **unknown**: it may have committed, so the new session is **kept** (its cookies are written) and the person is told to open Administration; if that asks them to sign in, to ask for a new link.
- **Two windows with the same link.** They queue on the Account's lock: one recovers, the other is refused as `used` and ends only its own session. Two windows pressed at the same moment can also trip over Auth: it keeps **one pending link per user**, so the loser's `verifyOtp` can fail because the winner's link replaced its own, and the winner's transaction deletes every other Auth session of the person, which can be the loser's, just made. Either way the loser asks the check again, a few times over about a second and a half (`recheckDelaysMs` in `lib/recovery.ts`), whether the token has been used; once it has, the loser shows the one bad-link message. If the token stays valid the cause was something else and the loser says "try again" (retryable). The loser never writes a cookie, so in two tabs of one browser it cannot leave its own session, or an expiry, over the winner's. The winner is never harmed.

**The marker.** Recovery gives the new session the fresh authentication an Administrator needs for the invitation and Accounts pages, without a step-up (which needs a Google sign-in that, by assumption, does not work). The only edit this story makes to the step-up tables: `identity.fresh_authentications.nonce_id` is now nullable, a `source` column (`step_up` or `recovery`) says where a marker came from, a check constraint ties the two (`(source = 'step_up') = (nonce_id is not null)`), and the guard trigger compares the nonce with `is distinct from` (so a recovery's NULL cannot slip through) and forbids changing `source`. The marker is the `administration` class, for 5 minutes, for that one session; other classes and other sessions have none. `api.use_marker`, `api.complete_step_up` and `api.revoke_grants` are unchanged.

**Audit events** (append-only `identity.audit_events`; actor `system:recovery` or `user:<Auth user ID>`, an opaque target `account:<id>`; never a token, a hash, an address or a reason): `recovery.issued`, `recovery.limited`, `recovery.rejected.<unknown|used|expired|voided|administrator>`, `recovery.mail_failed` and `recovery.redeemed` (and the `session.revoked` and `account.epoch_raised` events of the grants and epoch it moves). Refusals (`recovery.limited` and `recovery.rejected.*`) are recorded **once an hour** per actor, action and target, under an advisory lock, so a flood of bad attempts grows nothing.

**Privacy.** Neither page nor the mail shows an address, a name, a Workspace or anyone's projects. The token appears only inside the mailed link and the form's hidden field: never in a URL the server sees, a log, an audit row, a cookie, an error or browser storage. Every log line a recovery writes is a fixed message plus an error's name and message.

**The hosted preflight** (`api.preflight`, `check-env --live`, the Vercel build) now also reads `identity.recovery_tokens` and the marker's `source` column, checks from the catalog that the six functions of this story exist (`N3020`, "the Story 1.6 migration is not applied") and that the service role may execute the four it calls (`42501`), and carries every earlier probe forward. The environment contract grew by three variables, `RECOVERY_HASH_KEY`, `RESEND_API_KEY` and `APP_ORIGIN` (`docs/deployment-setup.md`, `docs/secrets.md`); the audited seed command needs neither of the last two.

**Known limits.**

- **What recovery covers, and what it does not.** The link is mailed to `ADMINISTRATOR_EMAIL`, which is usually the Administrator's own Google mailbox. Recovery therefore helps when **Google sign-in** is failing, misconfigured or blocked (an OAuth or provider problem, a lost second factor, a Google account that will not sign in to nova3D) **while that mailbox is still reachable**. It does **not** help when the Google account and its mailbox are themselves lost: there is then nowhere to send the link. That case, like a changed Google subject (below), remains the database runbook.
- **Anyone can use up the issuance budget.** The limits are global, as the Spine says, and `/recover` is public: anyone who can reach it can spend the one issuance per 15 minutes and the five per day (each also mails the Administrator), so a real recovery may have to wait. The Administrator's ordinary Google sign-in is not affected. Nothing mitigates it yet; an alarm on `recovery.limited` is Story 1.13 (`deferred-work.md`).
- **A mail whose outcome is unknown leaves its token valid**, by design (above).
- **Recovery re-pins nothing.** If the Administrator's Google subject changed, or the Auth user has a second Google identity (the locking-out case under Known limitations below), `identity.verified_google` offers no matching identity: `/recover` says "not available right now" and the audit holds `recovery.rejected.administrator`. That case is still the database runbook below.
- **Hosted Auth is unverified.** The Admin link API and `verifyOtp` were checked on the local stack with the Email provider off and Google the only provider (the user's `app_metadata` stays `google`, the new session's `amr` is `otp`, a replayed token answers `otp_expired`, and the new session keeps working after the others are deleted; a user with no identity row came back as `email`, so the tests use real identity rows). Whether hosted Auth allows both with the Email provider disabled is the check below (AC-4). **If it refuses either, stop and record a design change: the Spine allows the Google provider only, and enabling the Email provider is never the way around it.**
- **A mail system that rewrites links or drops fragments breaks the link.** Nothing here can see that; the first step of the hosted check looks at the link as received.

It adds one table and four functions, and widens the marker table without changing a row (`source` defaults to `step_up`); no setting or session is involved, the previous build never calls any of it, and **rolling back** is a redeploy of the previous build with the migration left in place. Set `RECOVERY_HASH_KEY`, `RESEND_API_KEY` and `APP_ORIGIN` in the staging Vercel project's Production scope first (the server and the build fail without them, and a preview must hold neither key). The Resend account must be registered with the Administrator's address (ledger item `resend-account`). The Hebrew of the new strings is machine-drafted like the rest and needs the native review (`deferred-work.md`).

## Accounts, invitations and the seed command (Story 1.3)

The accounts live in the database (below); the application half described above gates the app on them.

- **Accounts exist only through a database function.** Accounts and Workspaces live in the unexposed schemas `identity` and `projects`. The only callable surface is the `api` schema, whose functions only the service role may execute; `anon` and `authenticated` can execute and read nothing, and a function or table created later in these schemas is closed by default (default privileges, migration `*_accounts.sql`; see the note under Known limitations). A registration (`api.register_with_code`) locks the Auth user's row, records the attempt time, and creates the Account and its Workspace in one transaction. It is idempotent per command UUID: a retry, or a user who already has an Account, gets that Account back without spending any of the limiter's budget. A disabled Account is reported as `disabled`, never as a success.
- **Failures are generic and counted**: 5 per network origin per 15 minutes and 100 per hour across all origins, kept in Postgres. An unexpected database failure (a deadlock, a lock timeout) is not a bad code: it rolls the whole registration back, is not counted, and reaches the caller as an error.
- **Invitation codes** carry 160 random bits, are shown once, and only their HMAC-SHA256 under `INVITATION_HASH_KEY` is stored. Client addresses are likewise only stored as HMACs under `RATE_LIMIT_HASH_KEY`. Unused codes never expire; revoking a code never touches an existing Account. A general code is unique while unused; issuing another needs `--replace`. The Administrator's page (Story 1.11, below) issues and revokes through the very same two functions.
- **The Before User Created hook** (`[auth.hook.before_user_created]` in `supabase/config.toml`, function `api.before_user_created`) rejects every Auth user that is not a Google identity with a verified email, so email, phone and anonymous sign-ups cannot create a user even if a provider setting is wrong. Auth calls it for sign-up, the OAuth callback and invitations (the integration test sends an invitation with the service key and checks the rejection). The Auth admin create-user endpoint does not call it; it needs the service key. The hook never raises: a payload it cannot read is a rejection.
- **The audited seed command** writes every action to the append-only `identity.audit_events` with the actor `seed:<APP_ENV>:<operating-system user>`. It first checks that `APP_ENV` and `INSTANCE_ID` match the database it is about to write, and outside local it needs `--confirm <APP_ENV>`.

```sh
npm run seed:accounts -- preauthorize                  # ADMINISTRATOR_EMAIL as administrator, SEED_ACCOUNT_EMAILS as members
npm run seed:accounts -- unauthorize --email <address> # withdraw a pre-authorization nobody has used yet
npm run seed:accounts -- issue --name "Daniel"         # a named single-use code, printed once
npm run seed:accounts -- issue --general [--replace]   # the current general code; --replace revokes the current one
npm run seed:accounts -- list                          # invitation ID, kind, state, time and label; never a code
npm run seed:accounts -- revoke --id <invitation-id>   # or: printf %s "$CODE" | ... revoke --code-stdin
```

`SEED_ACCOUNT_EMAILS` is left unset in the templates on purpose: set it deliberately (comma-separated member addresses). `preauthorize` can be run as often as you like: each address has one pre-authorization. An address that already owns an Account is refused (error `N3001`), an address already pre-authorized with another role is refused (`N3002`), and a second Administrator address draws a warning. The first verified Google sign-in of a pre-authorized address activates exactly one Account and pins its Google subject (`api.consume_preauthorization`, called by the sign-in callback); a later sign-in with the same address under another Google subject is refused and audited (once an hour per user). An identity with no pre-authorization and no code gets no Account. Which environment each command needs: every command needs `APP_ENV`, `INSTANCE_ID`, `ADMINISTRATOR_EMAIL`, the Supabase URL and the service key (and checks them against the database's identity row). Beyond that, `preauthorize`, `unauthorize`, `list` and `revoke --id` need neither hashing key; `issue` and `revoke --code-stdin` need `INVITATION_HASH_KEY` only (they hash a code), and none needs `RATE_LIMIT_HASH_KEY`. The application itself needs all three hashing keys to start (`RECOVERY_HASH_KEY` joined them in Story 1.6; the seed command never reads it), in every environment except a preview, which must hold none of them (nor `RESEND_API_KEY`).

If `issue` fails or times out, its outcome is unknown: the code may have been stored. Run `list` and revoke by ID any invitation you do not recognise before issuing again.

### Known limitations

- **Fixed windows.** The limiter counts in fixed windows (15 minutes per origin, one hour overall), so an attacker who straddles a window boundary can make up to twice the limit of guesses (10 from one origin, 200 overall) in a short span. With 160-bit codes that is no practical gain.
- **The global limit can be used to lock registration.** Anyone who can send 100 wrong codes in an hour makes every registration `limited` until the window ends (at most an hour). Existing Accounts are not affected. An alarm on limiter trips is planned for Story 1.13.
- **Typographic details.** A code is matched after folding case, all whitespace, every hyphen or dash (ASCII hyphen, U+2010 to U+2015 and U+2212) and the look-alike letters (`O` as `0`, `I` and `L` as `1`), so a code survives being typed, pasted or read aloud. Input that is not shaped like a code after folding is refused without a database call. Client addresses are trusted only on Vercel (where the platform overwrites the forwarding headers); elsewhere every request shares one origin, and IPv6 addresses count by their /64 network.
- **Functions are closed by default, database-wide.** Postgres grants `EXECUTE` on every new function to PUBLIC, and a default-privileges rule limited to one schema cannot remove that. The migration therefore revokes it for every function the migration role (`postgres`) creates from now on, in any schema. Supabase's own default grants to `anon`, `authenticated` and `service_role` in the `public` schema still apply, so API functions there behave as before; but a future function that a Supabase service role must run (for example a trigger function on `auth.users`, run as `supabase_auth_admin`) needs an explicit `grant execute`.
- **A second Google identity locks the Account out.** Auth links a new Google identity to an existing user with the same verified email. The pinned-subject check treats any second Google identity on an Account's Auth user, like a replaced one, as a mismatch, so every session of that user is refused (and audited) until the extra identity is removed from Auth. That is deliberate: it is what stops a recycled address from using an Account. Administrator recovery (Story 1.6) does not fix this: it serves only an Account whose Auth user has exactly one Google identity, the pinned one, and it re-pins nothing, so for this case `/recover` says it is not available and the audit holds `recovery.rejected.administrator`. Removing the extra identity is a database operation (the runbook below).
- **Disabling revokes by epoch and by row.** A change of status raises the Account's epoch (above), so a disabled Account's sessions are refused and stay refused after it is enabled again; since Story 1.5, `api.disable_account` also marks every grant revoked (`disabled`, final) and deletes the person's Auth sessions in the same transaction (below).
- **Keys.** A hash key that no longer matches the one used to issue a code makes that code unredeemable without any error; there is no canary yet (see `deferred-work.md`).

### Runbook: a second Google identity locks an Account out (Josh)

**What it looks like.** Someone reports "That Google account cannot be used to sign in" (`not_allowed`) on an account that used to work, or the audit trail has `session.subject_mismatch` events. The cause: Auth links a new Google identity to an existing user with the same verified email, and the gate treats an Auth user with a second Google identity (or a replaced one) as no longer the identity pinned to the Account. Every session of that user is then refused and signed out. That is the gate working: it is what stops a recycled address from using someone else's Account. Do not remove it; remove the extra identity once you have decided it should go.

1. **Find the events.** In the Supabase SQL editor of the environment:

   ```sql
   select id, occurred_at, actor, action, target
     from identity.audit_events
    where action = 'session.subject_mismatch'
    order by id desc limit 20;
   ```

   An event reads `actor = system:authorization`, `action = session.subject_mismatch`, `target = session:<session id>`. It carries no email, token or address. (The same session can only appear once: only the request that revoked the grant writes it.)
2. **Find the Account and the identities.**

   ```sql
   select a.id as account_id, a.user_id, a.role, a.google_subject as pinned_subject
     from identity.session_grants g join identity.accounts a on a.id = g.account_id
    where g.session_id = '<session id from the event>';

   select id, provider_id, created_at, last_sign_in_at, identity_data ->> 'email' as email
     from auth.identities
    where user_id = '<user_id>' and provider = 'google'
    order by created_at;
   ```

   The identity whose `provider_id` equals `pinned_subject` is the Account's own. Any other Google identity is the extra one. If the pinned one is the one that is gone or changed, stop: that is the Administrator re-pin case, which Administrator recovery (Story 1.6) deliberately does not handle (it re-pins nothing) and which stays a database operation (see `deferred-work.md`); the Account cannot be repaired from here.
3. **Decide, then remove the extra identity.** If it should not be there (a recycled or unknown address), delete just that row, using its `id` from the second query:

   ```sql
   delete from auth.identities where id = '<identity id>' and user_id = '<user_id>' and provider = 'google' and provider_id <> '<pinned_subject>';
   ```

   If you are not sure whose it is, leave it: the Account stays locked out, which is the safe state.
4. **End every session the extra identity may have opened**, whatever the gate has already refused, by raising the Account's epoch (audited as `account.epoch_raised`; every grant issued before it is refused from then on):

   ```sql
   select * from api.raise_authorization_epoch('<account_id>', 'operator:josh');
   ```

5. **Tell the owner to sign in again.** Their grants were revoked with the reason `subject_mismatch` and stay refused (a revoked grant is final); a new sign-in issues a new one. If the Account still says "not allowed", step 2 shows an identity you did not remove.

### Browser tests

`npm run test:e2e` runs against a production build and the local stack. Local Google sign-in cannot be driven, so `tests/e2e/registration.spec.ts`, `tests/e2e/authorization.spec.ts`, `tests/e2e/request-integrity.spec.ts`, `tests/e2e/signed-in-shell.spec.ts` (the shell on the real routes: keyboard, menus and dialogs, the 404 page, enlarged text, high contrast and axe in four variants) and `tests/e2e/preferences.spec.ts` (adoption at the first sign-in, a new device, a change from another device, a save that fails, the sign-in page's choices) and `tests/e2e/invitations.spec.ts` (the Administrator's invitation page, Story 1.11: who sees it, a change refused without a fresh sign-in, a code shown once, revoking, the general code, the database not answering, axe in four variants and 320 px at 200% text; it also forges the Administrator's role and, where a flow needs one, the marker a completed step-up writes, and the tests that touch the one general code take a database lock so the desktop and phone projects do not trip over each other; the real step-up from the page is in `tests/e2e/step-up.spec.ts`) forge sessions (`tests/support/forged-session.ts`): it inserts a Google user and an `auth.sessions` row into the local database, signs an HS256 access token with the stack's JWT secret (with `session_id`), and sets the `@supabase/ssr` cookie in the browser. A forged session gets its grant the way the application gives one (`issue_grant`), or none, to test the cutover. The Auth service still validates the token, so the application's real `getUser()`, proxy and authorization checks run; only the Google round trip, and with it the callback's code exchange, is skipped (the callback is covered by unit tests with a fake Auth client). The tests read the keys the server runs with from `.env.local` (or the environment, which wins, as it does for Next.js) and refuse to run unless the server is pointed at the local stack. They issue their own codes under the server's `INVITATION_HASH_KEY`, create their own users and remove them afterwards (audit events are append-only and stay). The registration limiter counts every test browser as one origin, so the registration file runs in order and clears the limiter before each test.

The Administrator recovery specs (Story 1.6) are described under Administrator recovery above: `tests/e2e/recovery.spec.ts` (one serial spec, desktop project only, reading the recovery mail from the stack's Mailpit) and `tests/e2e/recovery-pages.spec.ts` (the pages on desktop and phone), with the servers started under `ADMINISTRATOR_EMAIL=recovery-admin@example.test`.

"The database is unreachable" is made true for one user at a time on a **second application server**: `test:e2e` starts the same build on the configured port plus one (never reusing a server that is already there) with `tests/support/fake-network.mjs` preloaded (`NODE_OPTIONS` is appended to, and the preload is given as a file URL). The preload refuses to load unless `playwright.config.ts` has set `NOVA3D_FAKE_NETWORK=playwright` and handed it a private control directory made with `mkdtemp`, removed when the run ends. The preload wraps the server's `fetch`; a test switches an outage on for one user ID by writing a file (`tests/support/fake-network.ts`), and every call to the accounts API for that user, optionally for chosen functions only, then fails as a dropped connection or as a 503. A call that names nobody (`list_invitations`, which takes no argument) cannot be attributed to a user, so it has a switch of its own that is global to that server (`startGlobalOutage`); the invitation tests that use it, and the ones that load the page through that server, take a database lock so they take turns. Other users, the first server and the application's own code are untouched, and the preload also counts the calls it sees, which is how a test proves that a page costs one authorization call in the proxy and one in the page.

### The fake Google (Story 1.4b)

The step-up needs a real second sign-in: a new Auth session, a real `auth.mfa_amr_claims` row, the callback's code exchange. The local stack cannot reach Google, so `tests/support/fake-google.mjs` stands in for it, and `scripts/fake-google-stack.mjs` wires it in:

```sh
supabase start
node scripts/setup-env.mjs local        # as before
npm run fake-google:up                  # starts the fake and swaps ONLY the stack's Auth container
npm run build && npm run test:e2e       # the step-up flows now run instead of being skipped
npm run fake-google:down                # puts the original Auth container back (supabase stop also removes it)
```

How it works. Auth ignores a configured provider URL for Google: it reads Google's OpenID discovery document from the fixed address `https://accounts.google.com`, verifies a signed `id_token`, and takes the authorization endpoint from the document. So the swap recreates the Auth container (same image, command, labels, network, aliases, health check and environment) with: random Google client ID and secret (the stack has none), `HTTPS_PROXY` pointing at a tunnel on the host that serves `accounts.google.com:443` and refuses every other host, `NO_PROXY` set to `localhost,127.0.0.1,host.docker.internal` (it REPLACES whatever the container had), `SSL_CERT_FILE` naming the fake's throwaway CA (Go reads it INSTEAD of the system roots, so while the swap is in place the Auth container trusts that CA alone and no real HTTPS server), and the application callbacks of the test servers (`127.0.0.1:4173` and `:4174`, or `PORT` and `PORT + 1`) added to `GOTRUE_URI_ALLOW_LIST`. The fake serves the account chooser on `127.0.0.1:9099` (loopback only, with a small control API the tests use to register Google accounts and read what the application asked for; it answers only a request whose Host is `127.0.0.1:9099` or `localhost:9099` and that is not marked `Sec-Fetch-Site: cross-site`, so a web page, or a DNS name rebound to this address, cannot drive it from the person's browser), the token endpoint and signing keys on the next port (the only part the container reaches), the tunnel on the one after, and the discovery document over TLS on the fourth. The token and tunnel listeners bind every interface, because the Auth container reaches the host over Docker's bridge and no single address is the same on every machine; what they offer there is a token endpoint that needs a one-time 128-bit code, a public key set and a tunnel to one name. It honors `prompt=select_account` like Google (always the chooser) and otherwise passes a browser that already chose an account straight through. Ports 9099 to 9102 must be free on the machine (the script fails with the reason if they are not). The swap then proves itself: Auth must answer an authorize request with a redirect to the fake's chooser, after fetching the fake's discovery document; if not, the original container is put back, the half-made container and the fake are removed, and the script fails. `npm run fake-google:status` checks the same thing at any time (the fake answers, Auth is swapped, and Auth really sends Google sign-in to the fake); CI runs it right after the swap. Running `up` again while Auth is already swapped, or after the stack was restarted with a fake still running, first stops that fake (only a process that `/proc` says is still a `fake-google.mjs`, never a recycled process ID) and puts the original back, then swaps again. The script's state (a pointer to the running fake, the saved original container, the fake's run directory) lives in a directory created 0700 that it trusts only while it is a real directory owned by the current user with no group or other access. The restore is a rebuild from `docker inspect` of the original (image, command, user, labels, network and aliases, hosts, restart policy, a CMD-SHELL health check and environment); it does not carry bind mounts, port bindings, resource limits or other health check kinds, which the Supabase CLI's Auth container does not use today. If it ever misbehaves, the recovery is `supabase stop` then `supabase start`.

It is test support only and local only: dependency-free (Node built-ins and the `openssl` command), it generates its CA, its certificate and its `id_token` signing key at run time in a private temporary directory (mode 0700, removed when it stops; the CA's own key is deleted as soon as the certificate is signed), and nothing in the repository is a key or a certificate (a unit test scans for them). It never touches a hosted project and never changes `supabase/config.toml`, which is what hosted settings are diffed against (a unit test pins that). CI runs `npm run fake-google:up` after the unit and integration suites and before the browser tests; without the swap, the step-up flows that need it are skipped locally (also when the fake still runs but the stack was restarted, which the specs detect by asking Auth) and **fail in CI**, so a missing swap cannot pass for a green run. The step-up page, the start of a step-up and "use a different Google account" are tested without it, by stopping the browser at Auth's authorize endpoint.

No OAuth secret belongs in the repository or in a `NEXT_PUBLIC_*` variable. `/api/health` reports public Supabase configuration state, and the login page exposes Google only.
